PART 0 · 0:00–0:30

GitHub 기본 개념과 왜 쓰는가

버튼을 누르기 전에 "무엇을 왜 하는지"부터 잡아요. 이 개념이 잡혀 있으면 AI에게 일을 시킬 때도, 개발자와 대화할 때도 같은 말로 이야기할 수 있어요.

0-1. 파이썬 수업에서 이어지는 질문

지난 시간에는 Colab 노트 한 개에 코드를 쓰고 실행했어요. 그런데 실제 서비스는 파일 하나로 끝나지 않아요. 웹페이지 한 장만 해도 HTML, CSS, 자바스크립트, 이미지 파일이 함께 움직이고, AI 코딩 도구에게 "로그인 기능 붙여 줘"라고 한 번 말하면 여러 파일이 한꺼번에 바뀌어요.

질문 1

어디에 두나?

여러 파일로 된 프로젝트를 한곳에 모아 두고, 다른 컴퓨터나 다른 사람도 같은 것을 볼 수 있어야 해요.

질문 2

망가지면?

AI가 고친 뒤 화면이 깨졌을 때, "어제 잘 되던 상태"로 돌아갈 수 있어야 해요.

질문 3

누가 무엇을?

나, 동료, 개발자, AI가 함께 고칠 때 누가 언제 무엇을 왜 바꿨는지 남아야 해요.

이 세 질문에 답하는 도구가 Git과 GitHub예요.

0-2. Git과 GitHub는 다른 것

둘은 이름이 비슷해서 자주 섞어 부르지만, 역할이 달라요.

Git (깃)

파일의 변경 기록을 남기는 버전 관리 도구예요. 내 컴퓨터 안에서 동작하고, 인터넷이 없어도 쓸 수 있어요. 2005년 리눅스 개발자 리누스 토르발스가 만들었어요.

vs
GitHub (깃허브)

Git으로 관리하는 프로젝트를 인터넷에 올려 두고 함께 일하는 서비스예요. 보관, 공유, 리뷰, 이슈 관리, 배포까지 협업 기능을 더해 줘요.

비유하면 Git은 문서 프로그램의 "버전 기록" 기능, GitHub는 그 문서를 올려 두고 팀이 함께 댓글 달고 승인하는 공유 드라이브예요. 오늘은 설치 없이 GitHub 웹 화면만으로 Git의 핵심 동작을 해 봐요.

바이브코더가 알아 둘 점
클로드 코드 같은 AI 코딩 도구는 내 컴퓨터(또는 클라우드 작업 공간)에서 Git 명령어를 대신 실행해요. 명령어를 외울 필요는 없지만, "커밋해 줘", "푸시해 줘", "이 커밋으로 되돌려 줘"가 무슨 뜻인지 알아야 AI에게 정확히 시키고 결과를 확인할 수 있어요.

0-3. 왜 써야 하나: 4가지 이유

이유GitHub 없이GitHub로오늘 해 보는 곳
① 세이브 포인트"index_최종_진짜최종.html"을 계속 만들고, 망가지면 어느 파일이 마지막으로 잘 되던 것인지 모름저장할 때마다 메모가 붙은 기록(커밋)이 쌓이고, 언제든 그 시점으로 돌아갈 수 있음1-5, 1-6
② 변경 기록"이거 누가 바꿨어요?"를 메신저로 묻고 다님누가, 언제, 어떤 줄을, 왜 바꿨는지 자동으로 남음2-2
③ 협업파일을 메일로 주고받다가 서로의 수정이 덮어써짐각자 갈래(브랜치)에서 작업하고, 검토(리뷰)를 거쳐 합침(병합)Part 3
④ 배포 연결완성 파일을 서버에 따로 올리는 작업이 매번 필요저장소의 특정 갈래가 바뀌면 웹사이트가 자동으로 갱신되게 연결할 수 있음4-4

특히 바이브코더에게 ①이 가장 중요해요. AI는 빠르게 많이 고치는 대신, 가끔 잘 되던 부분까지 함께 바꿔 버려요. AI에게 큰 작업을 시키기 전에 커밋을 남기는 습관이 있으면, 망가져도 몇 번의 클릭이나 한 문장으로 돌아올 수 있어요.

0-4. 오늘의 용어 지도

오늘 나오는 용어는 아래가 전부예요. 지금 다 외우지 않아도, 실습하면서 다시 돌아와 확인하면 돼요.

REPOSITORY

저장소

프로젝트 파일과 그 변경 기록을 모아 두는 폴더. 줄여서 "레포"라고 불러요.

COMMIT

커밋

변경 내용을 메모와 함께 기록하는 것. 게임의 세이브 포인트 한 칸이에요.

BRANCH

브랜치

원본을 건드리지 않고 따로 작업하는 갈래. 기본 갈래 이름은 main이에요.

REMOTE / LOCAL

원격 / 로컬

원격은 GitHub에 있는 저장소, 로컬은 내 컴퓨터(또는 AI 작업 공간)에 있는 복사본이에요.

PUSH / PULL / CLONE

푸시 / 풀 / 클론

푸시는 로컬 → 원격으로 올리기, 풀은 원격 → 로컬로 최신 받기, 클론은 원격 저장소를 기록째 처음 복사해 오기예요.

PULL REQUEST

풀 리퀘스트(PR)

"내 브랜치의 변경을 main에 합쳐 주세요"라는 요청. 여기서 검토와 의견이 오가요.

MERGE

병합

브랜치의 변경을 다른 브랜치에 합치는 것. 같은 줄을 서로 다르게 고쳤으면 충돌(conflict)이 나요.

ISSUE

이슈

할 일, 버그, 요청을 적어 두는 게시글. 담당자를 정하고 PR과 연결할 수 있어요.

RELEASE

릴리스

"이 시점이 v1.0이에요"처럼 특정 커밋에 이름표(태그)를 달아 공개하는 것이에요.

브라우저로 올릴 수 있는 크기
브라우저 업로드는 파일 하나당 25MiB, 한 번에 100개까지예요. 동영상이나 큰 데이터 파일은 저장소에 넣지 않는 것이 좋아요.

A: A의 PR을 먼저 병합해요.
B의 PR 화면: 충돌 때문에 바로 병합할 수 없다는 안내와 [Resolve conflicts] 버튼이 보이는지 확인해요.
B: [Resolve conflicts]를 누르면 두 문구가 표시 줄과 함께 보여요. 둘 중 하나(또는 합친 문구)만 남기고 표시 줄을 지운 뒤 [Mark as resolved] → [Commit merge]를 눌러요.
A: 충돌이 풀린 PR을 리뷰하고 병합해요.
충돌 화면에서 보이는 표시 예시
<<<<<<< fix/title-b
  <h1>이번 주만 특가</h1>
=======
  <h1>주말 한정 특가</h1>
>>>>>>> main

웹에서 풀 수 있는 충돌은 간단한 것뿐이에요
GitHub 웹에서는 줄 내용이 서로 다른 간단한 충돌만 풀 수 있고, 그 밖의 충돌은 명령줄에서 풀어야 해요. [Resolve conflicts] 버튼이 비활성화되어 있으면 AI 코딩 도구에게 "충돌 파일과 양쪽 내용을 보여 주고, 어느 쪽을 남길지 나에게 물어본 뒤 해결해 줘"라고 요청해요. 어느 쪽을 남길지는 요구사항을 아는 사람이 정해야 해요.

상용화를 위한 개발·운영 관리

실제 사용자가 쓰는 서비스가 되면 "고치는 곳"과 "사용자가 보는 곳"을 나눠야 해요. 이 파트는 PM이 개발팀과 출시 방식을 정할 때 알아야 할 구조와 장치를 다뤄요. 실습은 A의 저장소에서 짝과 함께 해요.

4-1. 개발과 운영은 왜 나누나

지금까지는 main을 고치면 그게 곧 결과물이었어요. 사용자가 생기면 이 방식은 위험해요. 실험 중인 기능, 아직 리뷰하지 않은 문구, AI가 잘못 바꾼 코드가 그대로 사용자에게 보이기 때문이에요.

환경누가 보나목적
로컬 (Local)작업하는 나, AI 코딩 도구고치고 바로 확인
개발·미리보기 (Preview / Staging)팀, PM, QA, 고객사 담당자운영과 비슷한 곳에서 확인·테스트
운영 (Production)실제 사용자검증을 마친 것만 공개

Vercel 같은 배포 서비스는 기본으로 이 세 가지 환경(Local, Preview, Production)을 나눠 제공하고, GitHub의 브랜치와 연결해 운영 브랜치(보통 main)는 운영으로, 다른 브랜치와 PR은 미리보기로 배포해요.

4-2. 브랜치 전략 두 가지

브랜치를 어떻게 나눌지는 GitHub가 정해 주지 않아요. 팀 규모와 출시 방식에 맞게 고르는 관례이고, 대표적으로 두 가지가 있어요.

A. main + 기능 브랜치

main = 운영. 모든 작업은 feature/… 브랜치에서 하고 PR로 main에 합쳐요. PR마다 미리보기 주소로 확인해요.

소규모 팀, 자주 내보내는 웹 서비스, 바이브코딩 프로젝트에 맞아요.

vs
B. main + develop + 기능 브랜치

main = 운영, develop = 개발 통합. 기능은 develop에 먼저 모아 스테이징에서 확인한 뒤, 출시할 때 develop → main으로 합쳐요.

출시 일정이 정해져 있거나, 고객사 검수를 거쳐야 하는 프로젝트에 맞아요.

1feature/…기능 작업
2PR → develop리뷰 후 개발 통합
3스테이징 확인PM·고객사 검수
4PR → main출시 승인
5운영 배포사용자에게 공개

위 흐름은 B 전략 예시예요. A 전략은 2~3단계 없이 PR 미리보기에서 확인하고 바로 main으로 합쳐요.

B 전략에서 이슈 자동 닫힘 주의
closes #번호는 기본 브랜치(main)로 병합될 때만 동작해요. develop으로 병합하는 PR에서는 이슈가 닫히지 않으니, 출시 PR(develop → main)에 해결한 이슈 번호를 모아 적거나 직접 닫아요.

저장소 하나에서 운영 사이트 하나를 공개하는 구조라서, PR마다 미리보기 주소를 따로 만들지는 않아요. PR별 미리보기가 필요하면 Vercel처럼 미리보기 배포를 제공하는 서비스를 GitHub에 연결해요. Vercel은 운영 브랜치가 아닌 브랜치에 커밋하거나 PR을 만들면 미리보기 배포를 만들고, 그 주소를 PR 댓글 등으로 보여 줘요. 무료 플랜의 GitHub Pages는 공개 저장소에서만 쓸 수 있어요.

GitHub의 Environments: 저장소 [Settings] → [Environments]에서 staging, production 같은 배포 환경을 만들고, 운영 배포 전에 지정한 사람의 승인(Required reviewers)을 받게 할 수 있어요. 무료 플랜에서는 공개 저장소에서만 설정할 수 있어요. 자동 배포(GitHub Actions)와 함께 쓰는 기능이라 오늘은 개념만 알아 둬요.

4-5. 릴리스와 롤백

운영에 내보낸 시점마다 이름표를 달아 두면, "v1.1 출시 뒤로 문의가 늘었다" 같은 이야기를 정확한 기록과 함께 할 수 있어요.

실습 15: v1.0.0 릴리스 만들기 (A의 저장소)

저장소 오른쪽 [Releases] → [Draft a new release]를 눌러요.
[Choose a tag]에 v1.0.0을 적고 새 태그로 만들어요. 대상(Target)은 main이에요.
제목에 셀렉트마켓 특가 페이지 첫 공개를 적고 [Generate release notes]를 눌러 병합된 PR 목록이 자동으로 채워지는지 봐요.
[Publish release]를 눌러요.

버전 번호 관례: v주.부.수(예: v1.0.0 → 기능 추가는 v1.1.0, 작은 수정은 v1.0.1) 형식을 많이 써요. GitHub가 강제하는 규칙은 아니고 널리 쓰이는 관례(시맨틱 버저닝)예요.

롤백(되돌려 내보내기): 출시 뒤 문제가 생기면, 원인이 된 PR을 1-6의 [Revert]로 되돌리고 병합해요. main이 바뀌면 배포도 따라 바뀌어요. 원인 파악은 그 다음에 해요. 롤백 PR도 기록으로 남아요.

4-6. 비밀 정보 관리

상용 서비스에는 API 키, 결제 키, 데이터베이스 주소 같은 비밀 정보가 들어가요. 이것이 저장소에 올라가면 공개 저장소에서는 누구나 볼 수 있고, 지운 뒤에도 커밋 기록에 남아요.

장치무엇을 하나
.gitignore커밋하지 않을 파일 목록. 비밀 정보를 담은 설정 파일(예: .env)을 여기에 적어 Git이 아예 기록하지 않게 해요. 저장소를 만들 때 함께 만들 수 있어요.
Secrets[Settings] → Security 영역의 [Secrets and variables] → [Actions]에 비밀 값을 저장하고, 자동 배포(GitHub Actions)에서 이름으로만 불러 써요. 값은 화면에 다시 보이지 않아요.
Push protection비밀 정보로 보이는 값이 담긴 푸시를 막아 줘요. 사용자 단위 보호는 공개 저장소에 대해 기본으로 켜져 있어요.
AI 코딩 도구 프롬프트 · 출시 전 점검
요청: 이 저장소에 비밀 정보가 커밋되어 있는지 점검해 줘.
내용: API 키, 토큰, 비밀번호, .env 파일이 현재 파일과 커밋 기록에 있는지 찾아. 찾은 값 자체는 화면에 다시 출력하지 말고 파일 이름과 줄 번호만 알려 줘. .gitignore에 .env가 들어 있는지도 확인해. 아무것도 고치거나 지우지 마.
형식: ① 발견 목록(파일·줄·종류) ② .gitignore 확인 결과 ③ 내가 해야 할 조치
이미 올라갔다면 키부터 바꿔요
비밀 정보가 한 번이라도 공개 저장소에 올라갔다면, 파일을 지우는 것보다 그 키를 발급한 서비스에서 키를 폐기하고 새로 발급하는 것이 먼저예요. 커밋 기록에는 이미 남아 있기 때문이에요.

WRAP-UP

오늘 정리

  • Git은 변경 기록 도구, GitHub는 그 기록을 인터넷에 두고 함께 일하는 서비스예요.
  • 바이브코더는 AI에게 큰 작업을 시키기 전에 커밋하고, 커밋 화면에서 AI가 실제로 무엇을 바꿨는지 확인해요. 되돌리기는 기록을 지우는 것이 아니라 되돌림 커밋을 쌓는 것이에요.
  • PM은 Commits·PR·Issues·Insights에서 진행을 확인하고, 의견은 줄 댓글·이슈·PR 리뷰처럼 기록이 남는 곳에 남겨요.
  • 두 명 이상이면 이슈 → 브랜치 → PR → 리뷰 → 병합 흐름으로 일하고, 충돌은 요구사항을 아는 사람이 정해요.
  • 상용화 단계에서는 운영과 개발을 나누고, 브랜치 보호·미리보기 환경·릴리스·롤백·비밀 관리로 운영을 지켜요.
