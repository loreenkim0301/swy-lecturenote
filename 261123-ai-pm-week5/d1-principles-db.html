SESSION 1 · 09:20–10:30

AI가 도구를 쓰는 방법: 툴 콜링·MCP·커넥터

4주차에 지메일 커넥터를 연결하고, 날씨 API를 붙였어요. 두 경우 모두 AI가 바깥 도구를 썼어요. 그 안에서 일어난 일은 같은 원리예요.

왜 하나?"상담 챗봇을 고도화해 주세요"라는 요청을 받으면, 기획자는 어떤 질문에 답하게 할지, 어떤 동작은 막을지 정해야 해요. 그 기능이 어떻게 만들어지는지 알아야 범위를 정할 수 있어요.

개념1-1. 툴 콜링: AI는 요청서를 쓰고, 실행은 내 프로그램이 해요

4주차 화요일에 이벤트 배너에 날씨를 붙였던 것 기억하시나요? 그때는 화면이 열리면 무조건 날씨 API를 불렀어요. 언제 부를지를 사람이 코드로 정해 둔 거예요.

툴 콜링은 다르게 움직여요. 고객이 "내일 배송 늦어질까요?"라고 물으면, AI가 스스로 날씨 도구를 쓸지 정해요. 다만 AI는 날씨를 직접 찾지 않아요. "날씨 도구를 서울로 써 줘"라는 요청서만 쓰고, 실제 실행은 내 프로그램이 해요.

클로드 공식 문서도 같은 순서로 설명해요. 도구마다 이름, 설명, 입력 값 모양을 알려 주면, 클로드는 사용자의 요청과 도구 설명을 보고 도구를 쓸지 정해요. 클로드가 tool_use 블록을 돌려주면 내 코드가 그 작업을 실행하고, 결과를 tool_result 블록으로 돌려줘요. 그러면 클로드가 그 결과로 원래 질문에 답해요.

구분내 프로그램에서 도는 도구Anthropic 서버에서 도는 도구
누가 실행하나내 프로그램Anthropic
예내가 만든 날씨 조회, 주문 조회웹 검색, 웹 페이지 가져오기, 코드 실행
내가 할 일실행하고 결과를 돌려주는 코드를 써요실행 코드가 필요 없고, 결과가 같은 답에 바로 담겨요
비용보통 API 요청과 같아요도구에 따라 요금이 더 붙을 수 있어요

출처: Claude 문서 Tool use(도구 정의 → tool_use 블록 → 내 코드가 실행 → tool_result로 돌려줌, 내 앱에서 도는 도구와 Anthropic 서버에서 도는 도구의 차이, 서버 도구는 사용량에 따라 요금이 더 붙을 수 있음) (2026-11-20 확인)

개념1-2. MCP와 커넥터는 툴 콜링 위에 있어요

먼저 4주차에 써 본 두 가지와 오늘 만들 툴 콜링을 나란히 놓고 구조를 비교해요. 가장 큰 차이는 바깥 도구를 언제 부를지 누가 정하는가, 그리고 도구를 실행하는 곳이 어디인가예요.

구분① 일반 API 호출② 툴 콜링③ MCP·커넥터
언제 부를지사람이 코드로 정해요AI가 정해요AI가 정해요
누가 실행하나내 코드내 프로그램MCP 서버(서비스 회사가 운영)
만드는 사람내 서비스 개발자내 서비스 개발자도구를 공개하려는 회사·개발자
기획자가 정할 것언제 부를지어떤 기능을 붙일지, 막을 동작어떤 커넥터를 켤지, 허락할 권한

세 가지는 아래처럼 층으로도 볼 수 있어요.

툴 콜링, MCP, 커넥터는 서로 경쟁하는 기술이 아니에요. 아래로 갈수록 바닥에 가까운, 서로 다른 층이에요.

층무엇인가누가 만드나여러분이 써 본 것
커넥터클로드 화면에서 [추가]를 눌러 연결하는 바깥 앱 연결서비스 회사가 만들고, Anthropic이 검토해 목록에 올려요지메일 커넥터, 구글 드라이브 커넥터
MCPAI 앱과 바깥 도구를 잇는 공개 표준 규격. 커넥터는 MCP 서버예요도구를 공개하려는 회사나 개발자커넥터를 연결할 때 보이는 'MCP'라는 말
툴 콜링AI가 도구 요청서를 쓰고 프로그램이 실행하는 기본 방식내 서비스를 만드는 개발자오늘 1-4에서 챗봇에 붙이는 날씨 도구

정리하면 이렇게 말할 수 있어요. 지메일 커넥터는 MCP로 만들어졌고, 클로드는 그 안의 도구들을 툴 콜링 방식으로 써요. 내 서비스에 도구를 하나 붙일 때는 툴 콜링을 바로 쓰고, 한 번 만든 도구를 여러 AI 앱에서 함께 쓰게 하고 싶을 때 MCP 서버로 만들어요.

기획자1-3. 상담 챗봇을 고도화한다면? 붙일 기능 정하기

4주차 월요일에 만든 상담 챗봇 기억하시나요? 이 챗봇은 FAQ와 운영 정책 안에서만 답해요. 그래서 고객이 "제 주문 어디쯤이에요?", "내일 비 오면 배송 늦어요?"처럼 지금 이 순간의 정보를 물으면 "확인 후 안내드릴게요"로 끝나요.

챗봇을 고도화한다는 것은 이렇게 막히는 질문에도 답하도록 기능을 더하는 일이에요. 1-1에서 본 툴 콜링이 그 기능을 만드는 방법이에요. 기획자는 아래 네 가지를 정해요.

  1. 고객이 지금 막히는 질문: 대화 기록에서 "확인 후 안내드릴게요"로 끝난 질문을 찾아요.
  2. 그 질문에 답하려면 붙일 기능: 날씨 조회, 주문 조회처럼 바깥 정보를 가져오거나 일을 처리하는 기능이에요.
  3. 읽기만 하는지, 바꾸기도 하는지: 바꾸는 기능일수록 실수했을 때 되돌리기 어려워요.
  4. 사람이 확인할 곳: 바꾸는 기능 앞에는 고객이나 상담원이 확인하는 단계를 둬요.

개념2-1. 멀티 에이전트란?

Anthropic은 클로드의 리서치 기능을 이 구조로 만들었다고 공개했어요. 리더 에이전트가 조사 계획을 세우고, 여러 에이전트가 질문의 서로 다른 부분을 동시에 찾아요. 내부 평가에서 리더 하나만 쓸 때보다 90.2% 더 좋은 결과가 나왔어요. 대신 토큰을 많이 썼어요. 에이전트 하나는 일반 채팅보다 약 4배, 멀티 에이전트는 약 15배의 토큰을 썼어요.

개념3-1. 랭체인과 크루AI는 무엇인가

4주차 수요일에 프레임워크는 기본 뼈대와 규칙을 미리 정해 둔 도구 묶음이라고 배웠어요. 랭체인(LangChain)과 크루AI(CrewAI)는 AI 에이전트를 만드는 프레임워크예요. 랭체인은 AI 모델, 도구, 검색을 이어 붙이는 부품을 많이 갖고 있어요. 크루AI는 역할을 나눈 여러 에이전트가 한 팀처럼 일하게 만드는 데 집중해요.

클로드에도 크롬 접근(클로드 인 크롬), MCP 커넥터, 컴퓨터 유즈가 이미 있어요. 그런데도 랭체인과 크루AI를 쓰는 이유는 쓰는 사람과 쓰는 곳이 다르기 때문이에요.

개념4-1. 데이터베이스 종류와 서비스 회사

개념4-2. 요즘 AI 개발에서 많이 쓰는 DB

2025년 Stack Overflow 개발자 설문에서 가장 많이 쓰는 데이터베이스는 PostgreSQL이었어요. 전체 응답자의 55.6%, 현업 개발자의 58.2%가 썼어요. PostgreSQL에는 pgvector라는 확장 기능이 있어서, 같은 데이터베이스 안에서 벡터 검색을 할 수 있어요. 그래서 벡터 전용 데이터베이스를 따로 두지 않아도 돼요. Supabase는 이 PostgreSQL을 바탕으로 만든 서비스예요.

정리하면 AI 서비스는 두 갈래로 만들어요. 원래 쓰던 데이터베이스에 벡터 검색을 붙이거나(PostgreSQL·MongoDB·Firestore), 벡터 전용 데이터베이스를 따로 둬요(Pinecone 등).

파이어스토어는 벡터 검색을 지원하지만, 임베딩은 저장하기 전에 직접 만들어야 해요. Anthropic도 자체 임베딩 모델을 제공하지 않아요. 그래서 파이어스토어와 클로드만으로는 ②가 비어요. 임베딩을 만드는 서비스를 따로 붙이거나, 임베딩 기능이 들어 있는 데이터베이스를 써야 해요.

개념4-4. 같은 챗봇, 세 가지 조합

기획자4-5. RAG 창고에 넣을 데이터 정하기

챗봇은 RAG 창고에서 찾은 내용을 답에 그대로 보여 줄 수 있어요. 그래서 RAG 창고에 고객 연락처나 주문 내역이 섞여 있으면, 질문 하나로 남의 정보가 답에 나올 수 있어요. AI 보안 위험 목록인 OWASP LLM Top 10에도 벡터와 임베딩의 약점(LLM08)이 들어 있어요. 접근 권한을 잘못 나누면 민감한 정보가 담긴 내용이 다른 사람에게 보일 수 있다고 경고해요.

오늘의 원칙

RAG 창고에는 '답의 근거로 고객에게 보여 줘도 되는 문서'만 넣어요. 회원 정보, 주문, 대화 기록은 메인 데이터베이스에 두고 RAG 창고로 복사하지 않아요.
