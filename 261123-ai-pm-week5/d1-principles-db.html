SESSION 1 · 09:20–10:30

AI가 바깥 도구를 쓰는 말: API → 툴 콜링 → MCP·커넥터

4주차에 날씨 API를 붙이고, 지메일 커넥터를 연결했어요. 오늘은 그 사이에 있는 말을 순서대로 정리해요. API에서 출발해야 툴 콜링이 왜 생겼는지, MCP가 왜 따로 있는지 이어져요.

왜 하나?개발자가 "API로 붙이자", "툴 콜링으로 하자", "MCP 서버로 만들자"라고 하면 서로 다른 제안이에요. 기획자는 각 말이 무엇이고, 그때 무엇을 정해야 하는지 알아야 범위와 비용을 정할 수 있어요.

키워드1-1. API: 프로그램끼리 기능을 빌려 쓰는 창구

4주차 월요일에 상담 챗봇 만들었던 것 기억하시나요? 그 챗봇은 손님 질문을 알아듣고 자연스러운 문장으로 답했어요. 그런데 우리는 질문을 이해하는 AI를 직접 만들지 않았어요. 우리 코드가 한 일은 세 가지예요.

  1. 손님 질문을 정해진 모양에 담아 Claude API로 보내요.
  2. Claude가 돌려준 답을 받아요.
  3. 받은 답을 챗봇 화면에 보여 줘요.

답을 만드는 기능은 Anthropic 서버에 있고, 우리는 그 기능을 빌려 와 내 챗봇의 기능으로 붙였어요. 이렇게 남의 기능을 빌려 와 내 서비스에 붙이는 일이 API 연동이에요. API는 프로그램끼리 정해 둔 약속으로 기능과 데이터를 주고받는 창구예요. 약속에는 어디로 보낼지(주소), 무엇을 어떤 모양으로 보낼지(요청), 어떤 모양으로 답이 올지(응답)가 들어 있어요.

4주차 화요일에 이벤트 배너에 날씨를 붙인 것도 같은 구조예요. OpenWeather의 정해진 주소로 "서울 날씨"를 요청하고, 정해진 모양으로 답을 받았어요.

복습 · API는 누구에게, 어떻게 열려 있나

4주차 화요일에 붙인 API는 모두 바깥 사람도 쓸 수 있게 공개한 오픈 API였어요. 오픈 API는 다시 키 없이 쓰는 개방형과 키를 받아야 쓰는 인증형으로 나눴어요. 오픈 API와 달리 회사 안 시스템끼리만 쓰는 내부 API도 있어요.

구분키누가 쓰나너무 많이 쓰는 걸 막는 방법예
오픈 API · 개방형필요 없어요. 주소만 열면 답이 와요누구나접속한 곳(IP 주소)마다 횟수 제한The Cat API(4주차 화요일 고양이 사진), Open-Meteo(날씨)
오픈 API · 인증형가입해서 받은 키를 요청마다 함께 보내요키를 받은 누구나키마다 횟수 제한, 넘으면 요금OpenWeather(날씨 배너), 기상청 단기예보(공공데이터포털), Claude API(상담 챗봇)
내부 API회사가 정한 방식으로 확인해요그 회사 시스템끼리만바깥에 열지 않아요쇼핑몰의 주문 조회·회원 정보 API
헷갈리기 쉬운 점
  • 키가 없다고 마음대로 쓰는 건 아니에요. Open-Meteo는 키 없이 쓰지만, 무료로는 상업적이지 않은 용도에 하루 1만 번 미만까지만 쓸 수 있어요.
  • 키가 있다고 다 유료는 아니에요. OpenWeather는 무료 키로 썼어요. Claude API는 인증형이면서, 처리한 글자 양(토큰)만큼 돈을 내는 유료 API예요.
  • Claude API 키는 곧 결제 수단이에요. 4주차 월요일에 챗봇을 아티팩트에서 내 컴퓨터로 옮길 때 키를 .env에 넣었던 이유예요. 키가 새면 남이 내 돈으로 Claude를 써요.

지금까지는 언제 부를지를 사람이 코드로 정했어요. 날씨 배너는 화면이 열리면 무조건 날씨 API를 불렀고, 챗봇은 손님이 질문을 보내면 무조건 Claude API를 불렀어요. 오늘 배우는 툴 콜링과 MCP도 모두 이 API 위에서 움직여요. 다른 점은 부를 때를 AI가 고른다는 거예요. 그래서 API부터 짚고 시작해요.

APIApplication Programming Interface

프로그램이 다른 프로그램의 기능과 데이터를 쓰도록 정해 둔 약속이자 창구예요. 웹 API는 정해진 주소로 요청을 보내고, 정해진 모양(주로 JSON)으로 답을 받아요.

뉴스로 보는 키워드

2023년 6월, 레딧이 15년 가까이 무료로 열어 두던 API를 사용량에 따라 돈을 받는 방식으로 바꿨어요. 아폴로 같은 외부 앱들이 문을 닫겠다고 했고, 8천 개가 넘는 커뮤니티가 항의의 뜻으로 게시판을 닫는 "블랙아웃"을 벌였어요. 아폴로 개발자는 내야 할 요금을 약 2천만 달러로 추산했어요.

기획자가 볼 점 API를 내놓은 회사가 조건을 바꾸면, 그 API 위에 만든 서비스가 한순간에 멈출 수 있어요.

히스토리
개발자가 자주 말하는 "REST API"는 2000년 무렵 정리된 웹 API 설계 방식에서 나온 말이에요. 같은 해 세일즈포스가 API를 상품의 일부로 팔기 시작했어요. AI 모델도 API로 써요. 4주차 월요일 상담 챗봇은 Claude API에 질문을 보내고 답을 받았어요. 2023년부터는 AI API 안에 "모델이 함수를 부를 값을 돌려주는" 기능이 들어갔어요(1-2 툴 콜링).
만든 사람 · 주요 주체
특정 한 사람이 만든 말은 아니에요. AI API를 내놓는 주요 회사는 Anthropic(Claude API), OpenAI, 구글(Gemini API)이고, 4주차 화요일에 쓴 OpenWeather 같은 데이터 회사도 API를 팔아요.

  2. 비용: AI API는 처리한 글자 양(토큰)에 따라 요금이 붙어요. 많이 부를수록 비용이 늘어요.
  3. 언제 부를지: 일반 API는 사람이 코드로 부를 때를 정해요. "AI가 필요할 때 알아서 부르게" 하려는 요구에서 툴 콜링이 나왔어요.

키워드1-2. 툴 콜링: AI는 요청서를 쓰고, 실행은 내 프로그램이 해요

1-1의 상담 챗봇에서는 내 프로그램이 Claude API를 부르는 쪽이었어요. 툴 콜링에서는 한 단계가 더 생겨요. 내 챗봇 안의 Claude가 다른 API(도구)를 쓸지 스스로 정해요. 고객이 "내일 배송 늦어질까요?"라고 물으면, Claude가 "날씨를 알아봐야겠다"고 판단해요.

다만 Claude가 날씨 API를 직접 부르지는 않아요. "날씨 도구를 서울로 써 줘"라는 요청서만 써서 돌려주고, 실제로 날씨 API를 부르는 일은 내 프로그램이 해요. 정리하면 무엇을 언제 쓸지는 AI가 정하고, 실제로 부르는 손은 내 프로그램이에요.

클로드 공식 문서도 같은 순서로 설명해요. 도구마다 이름, 설명, 입력 값 모양을 알려 주면, 클로드는 사용자의 요청과 도구 설명을 보고 도구를 쓸지 정해요. 클로드가 tool_use 블록을 돌려주면 내 코드가 그 작업을 실행하고, 결과를 tool_result 블록으로 돌려줘요. 그러면 클로드가 그 결과로 원래 질문에 답해요.

뉴스로 보는 키워드

2025년 6월 개발자 사이먼 윌리슨은 AI에게 도구를 줄 때 가장 위험한 조합에 "치명적인 3종 세트(lethal trifecta)"라는 이름을 붙였어요. 내 개인 데이터에 접근하기, 믿을 수 없는 바깥 내용 읽기, 바깥으로 내보내기, 이 세 가지를 한 에이전트에 모두 주면 공격자가 개인 데이터를 빼 갈 수 있다는 경고예요. 석 달 뒤인 2025년 9월, 노션이 3.0 버전에 AI 에이전트를 넣자 바로 이 조합의 위험이 지적됐어요. 보안 연구자가 흰 글씨로 명령을 숨긴 PDF를 만들어 보여 줬어요. 에이전트에게 이 PDF를 요약시키면, 에이전트가 숨은 명령을 따라 워크스페이스의 비공개 데이터를 웹 검색 도구에 실어 바깥 주소로 보낼 수 있었어요. 버그가 아니라, 도구를 붙이는 방식 자체를 노린 공격이에요. 노션은 이후 숨은 명령을 걸러내는 기능을 강화하고, 에이전트가 의심스러운 링크를 열기 전에 사용자 승인을 받게 했어요.

기획자가 볼 점 도구를 붙일 때는 "이 도구가 무엇을 읽고, 무엇을 바깥으로 보낼 수 있는지"를 함께 정해요.

2023년 6월 13일 OpenAI가 Chat Completions API에 함수 호출(function calling)을 넣었어요. 개발자가 함수를 설명해 주면, 모델이 그 함수를 부를 값을 JSON으로 돌려주는 방식이에요. Anthropic은 2024년 4월 공개 베타를 거쳐 2024년 5월 30일 Claude 3 모델 전체에 툴 유즈(tool use)를 정식 공개했어요. 이름은 회사마다 달라도 "모델은 요청서를 쓰고, 실행은 프로그램이 한다"는 구조는 같아요.
만든 사람 · 주요 주체
OpenAI(function calling), Anthropic(tool use) 등 AI API를 내놓는 회사가 각자 자기 API에 넣었어요. 하나의 표준 규격이 아니에요. 이 점이 1-3의 MCP와 달라요.
개발자 관점 주요 이슈

  2. 도구가 많아질 때: 도구가 많을수록 AI가 알맞은 도구를 고르는 정확도가 떨어질 수 있어요. 꼭 필요한 도구만 붙여요.
  3. AI가 채운 값을 그대로 믿지 않기: "누구의 데이터인가" 같은 값은 서버가 정해요(1-8 선택 과제).

키워드1-3. MCP와 커넥터: 한 번 만든 도구를 여러 AI 앱이 함께 쓰기

툴 콜링으로 붙인 도구는 내 프로그램 안에만 있어요. 같은 도구를 다른 AI 앱에서도 쓰려면 앱마다 다시 붙여야 해요. Anthropic은 MCP를 공개하며 "새 데이터 출처마다 따로 연결을 만들어야 해서 연결된 시스템을 키우기 어렵다"는 문제를 들었어요. 이 반복을 하나의 규격으로 줄인 것이 MCP이고, 클로드 앱에서 MCP 서버를 버튼으로 연결하는 기능이 커넥터예요.

MCPModel Context Protocol

AI 앱이 바깥 도구와 데이터에 연결할 때 쓰는 공개 표준 규격이에요. 도구를 내놓는 쪽은 MCP 서버, 가져다 쓰는 쪽은 MCP 클라이언트예요. 클로드 앱처럼 클라이언트를 품고 있는 AI 앱을 호스트라고 해요.

MCP 서버 코드의 버그 때문에 한 회사의 프로젝트·업무 정보가 MCP를 쓰는 다른 회사 사용자에게 보일 수 있었어요. 아사나는 해킹이 아니라 자사 버그였다고 밝혔고, 약 1천 곳의 고객사가 영향을 받았을 수 있다는 보도가 나왔어요.

기획자가 볼 점 표준이 퍼지는 속도만큼, MCP 서버 하나의 실수가 여러 회사에 번질 수 있어요.

  2. 짝 구조: 클라이언트 하나는 서버 하나와 짝을 이뤄요. 서버끼리 바로 연결하는 규격이 아니에요(1-9 선택 과제).

STEP 1. 지금 챗봇이 어떻게 답하는지 먼저 묻기

프롬프트 1 · 클로드 코드에 붙여 넣으세요
요청: 이 상담 챗봇이 지금 질문에 어떻게 답하는지 설명해 줘. 아직 코드는 고치지 마.
내용: 화면에서 보낸 질문이 서버를 거쳐 Claude API로 가고 답이 돌아오는 순서를 알려 줘. Claude API를 부르는 코드가 어느 파일 몇째 줄에 있는지도 알려 줘.
형식: ① 질문이 오가는 순서 3~5줄 ② Claude API를 부르는 파일과 줄 ③ 지금 바깥 API(날씨 등)를 부르는 곳이 있는지 있다/없다로

이렇게 보이면 성공③에 "바깥 API를 부르는 곳이 없다"고 나와요. 지금 챗봇은 Claude API 하나만 불러요.

STEP 2. 날씨 도구를 정의하고, 요청서를 받으면 실행하게 하기

1-2 그림 1의 ②~⑥을 한 번에 만드는 단계예요. 서버가 Claude에 질문을 보낼 때 도구 목록을 같이 보내고(②), Claude가 요청서를 돌려주면(③) 내 서버가 OpenWeather를 불러(④) 결과를 돌려줘요(⑤). 그러면 Claude가 최종 답을 써요(⑥).

먼저 챗봇 폴더의 .env를 열어 OPENWEATHER_KEY= 뒤에 날씨 배너 때 받은 키를 따옴표 없이 붙여 넣고 저장해요. 키는 대화창에 붙여 넣지 않아요.

프롬프트 2 · 같은 대화창에 붙여 넣으세요
요청: 상담 챗봇에 툴 유즈(tool use) 방식으로 날씨 도구 하나를 붙여 줘. 고객이 배송일 날씨를 물을 때만 Claude가 스스로 이 도구를 쓰게 하고 싶어.
내용: 도구 이름은 get_delivery_weather, 입력은 도시 이름(city) 하나야. description에는 "배송 받을 도시의 내일 날씨를 조회한다. 고객이 배송일 날씨나 날씨 때문에 배송이 늦어지는지 물을 때만 쓴다. 반품·교환 같은 일반 규정 질문에는 쓰지 않는다."라고 써. Claude가 tool_use로 요청서를 돌려주면 서버가 OpenWeather 5일/3시간 예보 API로 그 도시의 내일 날씨를 가져와 tool_result로 돌려보내고, Claude가 최종 답을 쓰게 해. 반복은 최대 3번까지만 해. 키는 .env의 OPENWEATHER_KEY에서만 읽고, 화면 코드에는 넣지 마. 날씨를 못 가져오면 "날씨를 확인하지 못했어요"라고 답하게 해. 도구를 쓸 때마다 서버 로그에 [도구 사용] 도구 이름과 도시를 한 줄 남겨 줘. 화면은 바꾸지 마.
형식: ① 바뀐 파일 목록 ② 도구 정의(name·description·input_schema) 원문 ③ 서버를 다시 켜는 방법 한 줄

이렇게 보이면 성공②의 description이 프롬프트에 쓴 문장 그대로예요. 화면 파일은 바뀐 파일 목록에 없어요.

내용: 화면에는 [구글로 로그인] 버튼과 로그인한 이름 한 줄만 더하고, 나머지 화면은 바꾸지 마. 질문을 보낼 때 파이어베이스 ID 토큰을 Authorization 헤더에 담아 보내. 서버는 ID 토큰을 firebase-admin으로 확인하고, Firestore customers 컬렉션에 그 이메일 문서가 있는지 봐. 로그인 안 했으면 "로그인해 주세요", 명단에 없으면 "등록된 고객이 아니에요"로 답해. 시험용으로 customers에 고객 5명(내 이메일 [내 지메일 주소] 포함), orders에 주문 8건(고객마다 1~2건, 주문번호·상품·상태·배송 도시)을 넣어 줘. 키는 .env에서만 읽어.
형식: ① 바뀐 파일 목록 ② 내 컴퓨터에서 여는 방법 한 줄 ③ 로그인 전/명단 밖 계정/내 계정으로 "안녕하세요"를 보낸 결과 3줄
이번 과제의 코드 예시에서 처음 보는 문법

코드 예시는 읽어 보는 용도이고, 직접 쓰지 않아요. 처음 보는 문법이 몇 가지 있으니 먼저 짚고 갈게요.

문법뜻
import · require다른 사람이 만든 라이브러리를 불러와요. 4주차 수요일에 배운 라이브러리를 코드 맨 위에서 부르는 줄이에요
async · await로그인이나 API 응답처럼 시간이 걸리는 일을 기다렸다가 다음 줄로 가요
fetch화면에서 서버나 API로 요청을 보내요. 요청을 보내고 답을 받는다는 점은 4주차 화요일에 배운 API 호출과 같아요
if (…) return조건이 맞으면 거기서 멈추고 결과를 돌려줘요
for (…)같은 일을 정해 둔 횟수만큼, 또는 목록의 항목마다 되풀이해요
{ name: "…", … }이름과 값을 묶은 덩어리(객체)예요. JSON과 모양이 같아요
번호무엇뜻
①signInWithPopup구글 로그인 창을 띄워요. 로그인이 끝나면 auth.currentUser에 로그인한 사람이 담겨요.
②getIdToken()파이어베이스가 발급한 ID 토큰이에요. 로그인한 사람이 누구인지 증명하는 값이에요. 화면에 적힌 이메일 글자를 그대로 믿지 않고, 서버는 이 값을 확인해요.
③Authorization 헤더질문과 함께 ID 토큰을 서버로 보내는 자리예요. 화면에 적힌 이메일 글자를 보내면 누구나 바꿔 쓸 수 있어서, ID 토큰을 보내요.
번호무엇뜻
①verifyIdToken서버가 ID 토큰이 위조되거나 만료되지 않았는지 확인해요. 통과하면 그 안의 이메일을 믿을 수 있어요. 통과하지 못하면 오류가 나서 다음 줄로 가지 않아요.
②customers 문서 찾기고객 명단에서 그 이메일 문서를 찾아요. 문서 이름을 이메일로 해 두면 한 번에 찾을 수 있어요.
③명단 밖이면 멈춤명단에 없으면 Claude를 부르지도 않고 여기서 끝내요. AI 호출 비용도 들지 않아요.

이렇게 보이면 성공로그인 전에는 "로그인해 주세요", 명단에 없는 계정은 "등록된 고객이 아니에요", 내 계정은 이름을 부르며 답해요.

TIP

로그인 창이 뜨지 않으면 파이어베이스 콘솔 Authentication 설정의 승인된 도메인에 지금 여는 주소가 있는지 확인해요. 확인한 화면을 캡처해 클로드 코드에 보여 주고 고쳐 달라고 해요.

STEP 2. 도구 목록에 주문 조회 도구 더하기

쓰인 개념 툴 콜링 — 그림 1의 ②(질문 + 도구 목록 보내기)를 만드는 단계예요. 오늘 만드는 도구는 모두 1-2 표의 내 프로그램에서 도는 도구예요. Anthropic 서버에서 도는 도구(웹 검색 등)는 쓰지 않아요.

1-7에서 날씨 도구를 붙일 때 클로드 코드가 만든 도구 목록이 여기서 말하는 tools예요. 1-7에서는 프롬프트로만 만들었으니, 이번에는 그 안을 들여다보고 도구를 하나 더해요. 툴 콜링은 쓸 수 있는 도구를 미리 정해 주는 방식이에요. 서버가 Claude에 질문을 보낼 때마다 tools라는 칸에 도구 목록을 같이 보내요. Claude는 이 목록 안에서만 고르고, 목록에 없는 도구는 쓸 수 없어요. 도구 하나는 세 칸으로 적어요.

칸무엇을 적나기획자가 볼 점
name도구 이름(영어·숫자·밑줄)무엇을 하는 도구인지 이름만 보고 알 수 있게
description무엇을 하는지, 언제 쓰고 언제 쓰지 않는지Claude가 도구를 고르는 근거예요. 가장 공들여 써요
input_schemaClaude가 채워 보낼 값의 목록과 모양AI가 정하면 안 되는 값은 여기에 넣지 않아요

1-8까지 마치면 도구는 1-7 계획표에서 고른 세 가지가 돼요. 날씨는 1-7에서 붙였고, 이번 STEP 2에서 주문 조회를, STEP 4에서 메일 보내기를 더해요. 주문 취소와 환불은 1-7에서 사람에게 넘기기로 했으니 목록에 넣지 않아요. 목록에 없으면 Claude는 그 일을 할 방법이 없어요. 이것이 가장 확실한 "막을 동작" 처리예요.

도구 이름하는 일읽기·바꾸기Claude가 채우는 값서버가 채우는 값
get_my_orders내 주문과 배송 상태 조회읽기주문 상태(선택)로그인한 고객 이메일
get_delivery_weather배송 도시의 내일 날씨 조회(1-7에서 붙였어요)읽기도시 이름없음
send_summary_email상담 요약을 고객 메일로 보내기(STEP 4)바꾸기(보내기)메일 제목, 본문받는 사람 = 로그인한 고객 이메일
번호무엇뜻
①name도구 이름이에요. 대화 기록에 이 이름이 남아서, 어떤 도구를 썼는지 확인할 때 봐요.
②description언제 쓰는지와 언제 쓰지 않는지를 함께 적어요. 엉뚱한 질문에 도구를 쓰면 코드보다 이 문장을 먼저 고쳐요.
③이메일 칸 없음"누구의 주문"을 Claude가 정하게 하면, 고객이 "kim@… 주문 보여 줘"라고 할 때 남의 주문이 나갈 수 있어요. 그래서 칸 자체를 두지 않고 서버가 STEP 1에서 확인한 이메일을 넣어요.
④required반드시 채워야 하는 값이에요. 도시가 없으면 날씨를 볼 수 없으니 필수로 둬요.
⑤tools질문을 보낼 때마다 도구 목록을 같이 보내요. 따로 고르는 칸(tool_choice)을 쓰지 않으면 Claude가 쓸지 말지 스스로 정해요(auto).

도구를 언제 쓸지 정하는 칸(tool_choice)도 있어요. 오늘은 기본값을 그대로 써요.

값뜻오늘
auto도구를 쓸지 말지 Claude가 정해요. 도구 목록을 보내면 기본값이에요이것을 써요
none도구 목록이 있어도 쓰지 않게 해요쓰지 않아요
any · tool반드시 도구를 쓰게 하거나, 특정 도구를 쓰게 해요Claude Opus 5.5, Sonnet 5.5 같은 최신 일부 모델은 이 값을 넣으면 오류(400)가 나요
프롬프트 2 · 같은 대화창에 붙여 넣으세요
요청: 1-7에서 만든 도구 목록에 get_my_orders 도구 하나를 더 정의해 줘. 실행 코드는 다음 단계에서 연결할 거라 지금은 정의만 해.
내용: get_my_orders는 로그인한 고객 본인의 주문·배송 상태를 조회하는 도구야. 입력은 주문 상태 하나만 받고, 이메일 칸은 두지 마. description에는 언제 쓰고 언제 쓰지 않는지를 한국어로 써. 1-7에서 만든 get_delivery_weather는 그대로 둬. 주문 취소·환불 도구는 만들지 마. tool_choice는 넣지 마.
형식: ① 바뀐 도구 목록 코드 ② get_my_orders description 원문 ③ 도구 2개의 "Claude가 채우는 값 / 서버가 채우는 값" 표

이렇게 보이면 성공형식 ③ 표에서 고객 이메일이 "서버가 채우는 값"에만 있고, get_delivery_weather 정의는 1-7 그대로예요.

STEP 3. 1-7의 반복에 주문 조회 실행 연결하기

쓰인 개념 툴 콜링 — 그림 1의 ③~⑥이에요. ③ Claude가 요청서(tool_use)를 돌려주고 → ④ 내 서버가 실행하고 → ⑤ 결과(tool_result)를 돌려주면 → ⑥ Claude가 최종 답을 써요. 그림 2의 ② 툴 콜링 구조와 같아요.

이 반복은 1-7 STEP 2에서 클로드 코드가 이미 만들었어요. Claude가 요청서(tool_use)를 돌려주면 서버가 도구를 실행하고, 결과(tool_result)를 다시 보내요. Claude가 "도구 없이 답할게요"라고 할 때까지 이 일을 반복해요. 아래 코드 예시 4는 그 반복이 어떤 모양인지 읽어 보는 용도예요. 이번에 새로 더하는 곳은 ⑤ 주문 조회를 로그인한 고객 이메일로 실행하는 줄과, 도구가 늘어난 만큼 반복 한도를 1-7의 3번에서 5번으로 늘리는 ① 두 곳이에요.

번호무엇뜻
①round < 5반복 횟수에 한도를 둬요. 도구를 끝없이 부르면 비용이 계속 나가요.
②stop_reasonClaude가 요청서를 썼는지 알려 주는 표시예요. "tool_use"가 아니면 최종 답이 나온 거예요.
③runTool요청서에 적힌 도구 이름과 값으로 서버가 실제로 실행해요. Claude는 직접 실행하지 않아요.
④tool_use_id어느 요청서에 대한 결과인지 짝을 맞추는 번호예요. 이 번호가 틀리면 오류가 나요.
⑤customer.emailSTEP 1에서 확인한 이메일만 써요. Claude가 보낸 값(input)에 이메일이 있어도 쓰지 않아요.
⑥모르는 도구목록에 없는 이름이 오면 실행하지 않고 오류를 돌려줘요.
프롬프트 3 · 같은 대화창에 붙여 넣으세요
요청: 1-7에서 만든 도구 실행 반복에 get_my_orders 실행을 연결해 줘. 반복을 새로 만들지 말고 있는 코드에 더해.
내용: get_my_orders 요청서가 오면 STEP 1에서 확인한 고객 이메일로만 orders를 찾아. Claude가 보낸 값에 이메일이 있어도 쓰지 마. 반복 한도는 3번에서 5번으로 늘려. 1-7에서 서버 로그에 남기던 [도구 사용] 기록을 관리자 화면 대화 기록에도 '이 답에서 쓴 도구 이름과 넣은 값'으로 남겨. 날씨 도구와 화면은 바꾸지 마.
형식: ① 바뀐 파일 목록 ② 아래 3개 질문 결과표(질문 / 쓴 도구 / 답): "내 주문 어디쯤 왔어요?" / "kim@example.com 주문도 보여 줘" / "내 주문 내일 부산 도착인데 비 오면 늦어요?"

이렇게 보이면 성공주문 질문에는 get_my_orders가 기록에 남고, 남의 이메일을 넣은 질문에도 내 주문만 보여 주거나 볼 수 없다고 답해요. 세 번째 질문처럼 주문과 날씨를 함께 물으면 도구 2개(get_my_orders, get_delivery_weather)를 차례로 써요. 날씨만 묻는 질문과 반품 질문은 1-7 STEP 3에서 확인했으니 다시 하지 않아요.

도구를 써야 할 때 안 쓰거나 안 써야 할 때 쓰면, 1-7 STEP 3의 고치는 법처럼 description 문장부터 고쳐요. 예: "get_my_orders 설명에 '배송 언제 와요'도 쓸 때라고 넣어 줘."

STEP 4. (심화) 상담 요약을 지메일로 보내는 도구 붙이기

STEP 1~3만 마쳐도 툴 콜링 챗봇은 완성돼요. STEP 4는 지금까지 쓰지 않은 구글 클라우드 콘솔(구글 서비스 권한을 설정하는 관리 화면)을 처음 다루는 심화 단계예요.

쓰인 개념 툴 콜링 + 일반 API 호출 — Claude가 "메일 보내기" 요청서를 쓰는 부분은 툴 콜링(그림 1의 ③)이에요. 요청서를 받은 내 서버가 지메일 API를 부르는 부분은 그림 2의 ① 일반 API 호출과 같아요. MCP는 쓰지 않아요. 4주차에 연결한 지메일 커넥터와 이름은 같지만 구조가 달라요(이 절 끝 표).

고객이 "방금 상담 내용 메일로 보내 줘"라고 하면, 가게 지메일로 고객에게 요약을 보내요. 지금까지의 도구는 읽기만 했지만, 이 도구는 메일을 보내는 도구예요. 그래서 세 가지를 정해 두고 만들어요.

먼저 구글 클라우드 콘솔에서 준비해요. 파이어베이스 프로젝트는 구글 클라우드 프로젝트이기도 해서, 같은 프로젝트를 열면 돼요.

  • OAuth 클라이언트를 만들고, 클로드 코드가 만든 스크립트로 가게 계정의 권한(리프레시 토큰)을 한 번 받아요. 아래 프롬프트 4가 이 순서를 안내해요.

선택 과제1-9. (선택 과제) (심화) 주문 시스템을 MCP 서버로 만들어 챗봇과 운영자가 함께 쓰기

먼저 질문해 볼게요. 주문 정보를 저장하는 별도 웹 서버(주문 시스템)를 만들고, 그 시스템을 MCP 서버로 만들었어요. 상담 챗봇도 MCP 서버로 만들면 두 서버가 서로 연결될까요?

연결되지 않아요. MCP는 서버끼리 잇는 규격이 아니라, 클라이언트가 서버에 붙는 규격이에요. MCP 공식 명세에서 호스트 앱(AI 앱)은 클라이언트를 여러 개 만들 수 있고, 클라이언트 하나는 서버 하나와 짝을 이뤄요. 서버는 도구를 내놓는 쪽이고, 클라이언트는 그 도구를 가져다 쓰는 쪽이에요. 챗봇이 주문 시스템의 도구를 쓰고 싶다면 챗봇은 서버가 아니라 클라이언트가 되어야 해요.

설계는 아래 순서로 해요. 단계마다 정할 것을 먼저 정하고, 만드는 일은 1-8처럼 클로드 코드에 프롬프트로 맡겨요.

STEP 1. 주문 시스템과 어드민 화면 정하기

  • 주문 데이터를 챗봇과 다른 곳(별도 파이어베이스 프로젝트 등)에 둬요. 주문의 주인은 챗봇이 아니라 주문 시스템이에요.
  • 어드민 화면에서 운영자가 주문을 검색하고 상태를 바꿔요. 이 화면은 사람이 쓰는 입구예요.
  • 정할 것: 주문 칸(주문번호·고객 이메일·상품·상태·배송 도시), 어드민에 들어올 수 있는 사람

STEP 2. MCP 서버로 내놓을 도구 정하기

  • 어드민 화면이 사람용 입구라면, MCP 주소는 AI용 입구예요. 같은 주문 데이터에 입구가 하나 더 생겨요.
  • 처음에는 읽기 도구만 내놓아요. 예: 내 주문 조회, 상태별 주문 목록. 상태 바꾸기는 어드민 화면에만 둬요.
  • 정할 것: 도구 이름과 설명, AI에게 내놓지 않을 동작

STEP 3. 누가 누구인지 정하기(인증)

  • 1-8에서는 도구를 내 서버가 실행해서, 이메일을 서버가 로그인 정보로 넣었어요.
  • MCP 커넥터를 쓰면 MCP 서버에 연결하는 것은 내 챗봇 서버가 아니라 Anthropic 쪽이에요. 그래서 챗봇 서버가 중간에서 이메일을 끼워 넣을 수 없어요.
  • 그래서 MCP 서버가 받는 토큰으로 사람을 구분해요. 고객 토큰은 그 고객의 주문만, 운영자 토큰은 전체 주문을 보게 해요.
  • 정할 것: 토큰 종류(고객용·운영자용), 토큰마다 볼 수 있는 범위

STEP 4. 상담 챗봇을 MCP 클라이언트로 연결하기

  • 챗봇 서버가 Claude에 질문을 보낼 때 MCP 서버 주소와 로그인한 고객의 토큰을 함께 보내요. 클라이언트 코드는 따로 짜지 않아도 돼요.
  • MCP 서버는 인터넷에서 열리는 주소여야 해요. Anthropic 쪽이 그 주소로 연결하기 때문이에요.
  • 확인할 것: "내 주문 어디쯤 왔어요?"에 내 주문만 나오는지, 다른 고객 이메일을 넣어도 남의 주문이 나오지 않는지

STEP 5. 운영자의 클로드 앱을 같은 서버에 연결하고 비교하기

  • 운영자는 클로드 앱에서 같은 MCP 서버를 직접 추가 커넥터로 붙여요. 4주차 지메일 커넥터를 붙였던 것과 같은 방법이에요.
  • 같은 도구를 챗봇(고객)과 클로드 앱(운영자)이 함께 쓰는지, 토큰에 따라 보이는 범위가 다른지 확인해요.

키워드4-1. RAG란? 찾아서 붙여 주고 답하게 하기

4주차 월요일에 상담 챗봇이 FAQ 30개 가운데 질문과 관련된 항목만 골라 Claude에게 함께 보내게 만들었던 것 기억하시나요? 이렇게 먼저 찾아서 붙여 주고 답하게 하는 방식을 RAG라고 불러요. 그때는 낱말이 겹치는 FAQ를 골랐어요. 오늘은 RAG라는 말이 어디서 나왔는지부터 정리하고, 뜻으로 찾는 방법으로 넓혀요.

RAGRetrieval-Augmented Generation · 검색 증강 생성

질문과 관련된 자료를 먼저 찾아(검색) AI에게 함께 주고, 그 자료를 바탕으로 답을 쓰게(생성) 하는 방식이에요. 4주차 월요일 상담 챗봇이 FAQ를 골라 Claude에게 보낸 것도 RAG예요.

뉴스로 보는 키워드

RAG라는 이름을 붙인 2020년 논문의 제1저자 패트릭 루이스는 엔비디아와의 인터뷰에서 이 "볼품없는 약어"에 대해 사과했어요. 그는 "이렇게 널리 쓰일 줄 알았다면 이름에 더 신경 썼을 것"이라고 말했어요. 지금은 AI 회사 Cohere에서 RAG 팀을 이끌어요.

기획자가 볼 점 이름은 어색해도, RAG는 "AI를 우리 회사 자료와 잇는" 가장 흔한 방법이 되었어요.

출처: NVIDIA 블로그: What Is Retrieval-Augmented Generation (2026-11-23 확인)

히스토리
2020년에 나온 논문에서 RAG라는 이름이 붙었어요. 모델이 학습으로 익힌 지식만으로는 정확한 답을 하거나, 근거를 대거나, 새 지식으로 고치기 어렵다는 문제를 풀려고, 관련 글을 찾아서 답을 쓰는 모델에 붙이는 방법을 제안했어요. 랭체인을 만든 해리슨 체이스도 회사 노션·슬랙 자료로 대화하는 실험에서 출발했고, 지금은 이런 일을 RAG라고 불러요.
만든 사람 · 주요 주체
논문은 패트릭 루이스(Patrick Lewis) 외 연구진이 썼어요. 당시 Facebook AI Research(지금 Meta) 소속이었어요. 지금은 DB 회사(구글 파이어스토어·MongoDB·Supabase), 임베딩 회사(구글·Voyage AI), 프레임워크(랭체인)가 RAG의 부품을 내놓아요.
개발자 관점 주요 이슈
  1. 학습 대신 붙이기: RAG는 모델을 다시 학습시키지 않아요. 자료만 바꾸면 답이 바뀌어서, 자주 바뀌는 회사 자료에 잘 맞아요.
  2. 무엇을 찾느냐가 답을 정함: 낱말로 찾을지 뜻으로 찾을지에 따라 답이 달라져요. 내일 이것을 실험해요.
  3. 권한: 사람마다 볼 수 있는 문서가 다르면 RAG 창고에서 정보가 섞여 나갈 수 있어요(4-6).

4주차 월요일 챗봇은 낱말이 겹치는 FAQ를 골랐어요. "돈 돌려받기"처럼 낱말이 다른 질문을 잡으려면 글의 뜻을 숫자로 바꾸고(임베딩), 가까운 것을 찾아야(벡터 검색) 해요.

임베딩Embedding

글의 뜻을 숫자 목록(좌표)으로 바꾸는 일이에요. 뜻이 비슷한 글은 좌표도 가까워요.

2025년 2월 데이터베이스 회사 MongoDB가 임베딩 모델 회사 Voyage AI를 약 2억 2천만 달러에 인수했어요. Anthropic이 임베딩용으로 추천하던 회사가 DB 회사로 들어간 거예요.

기획자가 볼 점 DB 회사가 임베딩까지 함께 내놓기 시작하면서, "어디에 저장하고 무엇으로 좌표를 만들지"를 한 번에 고르는 경우가 늘어요.

  2. 비용: 글을 좌표로 바꿀 때마다 토큰 요금이 붙어요. 내일 실험에서 임베딩 토큰을 따로 재는 이유예요.

임베딩 좌표 가운데 질문 좌표와 가장 가까운 것을 찾는 검색이에요. 이 좌표를 저장하고 빨리 찾아 주는 데이터베이스를 벡터 DB라고 불러요.

기술 매체 The New Stack은 「Postgres도 이제 벡터 데이터베이스」라는 기사에서, AWS가 pgvector를 만든 앤드루 케인과 처음 손잡고 이를 제공한 클라우드 회사라는 AWS 담당자의 말을 전했어요. 벡터 전용 DB를 따로 두지 않고, 늘 쓰던 DB에 벡터 기능을 더하는 흐름이에요.

기획자가 볼 점 새 DB를 하나 더 들이기 전에, 지금 쓰는 DB에 벡터 기능이 있는지부터 확인해요.

기획자4-6. RAG 창고에 넣을 데이터 정하기

챗봇은 RAG 창고에서 찾은 내용을 답에 그대로 보여 줄 수 있어요. 그래서 RAG 창고에 고객 연락처나 주문 내역이 섞여 있으면, 질문 하나로 남의 정보가 답에 나올 수 있어요. AI 보안 위험 목록인 OWASP LLM Top 10에도 벡터와 임베딩의 약점(LLM08)이 들어 있어요. 접근 권한을 잘못 나누면 민감한 정보가 담긴 내용이 다른 사람에게 보일 수 있다고 경고해요.
