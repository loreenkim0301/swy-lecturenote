SESSION 1

GitHub 기본 개념과 왜 쓰는가

버튼을 누르기 전에 "무엇을 왜 하는지"부터 잡아요. 이 개념이 잡혀 있으면 AI에게 일을 시킬 때도, 개발자와 대화할 때도 같은 말로 이야기할 수 있어요. 오늘은 코드를 한 줄도 쓰지 않고 웹 화면만으로 GitHub를 써요.

1-1. 버전 관리, 이미 매일 하고 있어요

버전 관리는 파일이 바뀌어 온 과정을 기록해 두고, 필요할 때 예전 상태를 찾거나 되돌리는 일이에요. 개발자만의 일이 아니에요. 기획서·보고서·디자인 시안·엑셀을 다루는 사람이라면 누구나 이미 매일 버전 관리를 하고 있어요. 다만 대부분 "파일 이름"으로만 하고 있을 뿐이에요.

업무 장면이럴 때 생기는 문제
폴더에 기획서_최종.docx, 기획서_최종_진짜최종.docx, 기획서_최종_수정2.docx가 쌓여 있어요.어느 것이 진짜 마지막인지, 무엇이 바뀌었는지 아무도 몰라요.
팀장님께 메일로 보냈더니 수정본이 회신으로 오고, 다른 동료도 따로 고쳐서 보냈어요.두 수정본을 손으로 합치다가 한쪽 수정이 빠져요.
공유 드라이브의 엑셀을 두 사람이 동시에 고쳤어요.나중에 저장한 사람이 앞사람의 수정을 덮어써요.
클라이언트가 승인한 시안과 지금 작업 중인 시안이 같은 폴더에 있어요.승인 안 된 버전을 실수로 보내요.
"지난주 화요일 버전으로 돌려 주세요"라는 요청이 왔어요.그날 저장한 파일이 남아 있지 않거나, 어느 것인지 찾을 수 없어요.

업무에서 파일 버전을 잘 관리하는 대표 팁

팁이렇게 해요
1. 파일 이름 규칙 정하기날짜_문서명_v번호_작성자처럼 순서를 정해 팀이 함께 써요. 예: 20261028_특가기획서_v03_김수정.docx
2. "최종"이라고 쓰지 않기"최종"은 한 번 더 고치는 순간 거짓이 돼요. 대신 날짜와 버전 번호를 붙여요.
3. 번호를 건너뛰지 않기v01 → v02 → v03처럼 하나씩 올려요. 번호만 봐도 순서가 보여요.
4. 바꾼 내용을 한 줄로 남기기버전마다 "무엇을, 왜, 누구 요청으로" 바꿨는지 변경 이력표나 메모에 한 줄씩 적어요. 되돌릴 때 판단이 쉬워져요.
5. 원본은 두고 사본으로 작업하기크게 고치기 전에는 사본을 먼저 만들어요. 덮어쓰기 사고를 막는 가장 쉬운 습관이에요.
6. 승인본·전달본은 따로 두고 고치지 않기클라이언트에게 보낸 버전, 결재받은 버전은 별도 폴더에 두고 손대지 않아요.
7. 도구의 "버전 기록" 기능 쓰기구글 문서·시트, 마이크로소프트 365 같은 클라우드 문서는 자동으로 버전 기록이 남아요. 중요한 시점에는 버전에 이름을 붙여 두세요.
8. 규칙은 단순하게, 팀과 합의하기규칙이 복잡하면 아무도 안 지켜요. 지킬 수 있는 한두 가지부터 팀이 함께 정해요.

1-2. GitHub에도 같은 개념이 있어요

위의 팁들은 GitHub에서 대부분 기능으로 이미 들어 있어요. 파일 이름에 번호를 붙이지 않아도, GitHub가 저장할 때마다 기록을 남겨 줘요.

업무에서 하던 일GitHub에서는오늘 해 보는 곳
팀이 함께 쓰는 공유 폴더저장소(Repository): 프로젝트 파일과 변경 기록을 모아 두는 곳3-1
v01, v02… 버전 번호와 날짜커밋(Commit): 저장할 때마다 누가·언제 바꿨는지 자동으로 남는 기록3-2

"지난주 버전으로 돌려 주세요"과거 보기·되돌리기: 커밋 기록에서 예전 상태를 보고 되돌림3-5, 3-6
원본은 두고 사본으로 작업하기브랜치(Branch): 원본(main)은 그대로 두고 따로 고치는 갈래3-8

1-3. 우리가 GitHub를 배우는 핵심 이유: 올리고 내리기

한 문장으로 말하면
우리가 만들었거나 보관하고 있는 파일을 GitHub에 올리고(업로드·푸시), 필요할 때 다시 내려받기(다운로드·클론·풀) 위해서예요. 올릴 때마다 기록이 남는 것은 덤이에요.
1내 작업 공간내 컴퓨터, 또는 Claude가 일하는 공간
2올리기GitHub 저장소에 기록과 함께 보관
3내리기다른 컴퓨터·다른 사람·AI가 같은 파일을 받아요
4공개하기GitHub Pages로 누구나 여는 웹 주소

AI로 만든 결과물은 대부분 파일이에요. 파일을 한곳에 올려 두면 어느 컴퓨터에서든, 어떤 AI 도구로든 이어서 고칠 수 있고, 그대로 웹사이트로 공개할 수도 있어요(세션 5).

1-4. AI와 함께 만들면 생기는 세 가지 질문

실제 서비스는 파일 하나로 끝나지 않아요. 웹페이지 한 장만 해도 HTML, CSS, 자바스크립트, 이미지 파일이 함께 움직이고, AI에게 "로그인 기능 붙여 줘"라고 한 번 말하면 여러 파일이 한꺼번에 바뀌어요. 문서도 마찬가지예요. "최종", "최종_진짜", "최종_수정2" 파일이 쌓이면 어느 것이 맞는지 아무도 몰라요.

누가 무엇을?

나, 동료, 개발자, AI가 함께 고칠 때 누가 언제 무엇을 왜 바꿨는지 남아야 해요.

이 세 질문에 답하는 도구가 Git과 GitHub예요. 한 문장으로 말하면 GitHub는 파일을 온라인 보관함(저장소)에 올려 두고, 누가 언제 무엇을 바꿨는지 기록을 남기며 함께 일하는 서비스예요.

1-5. Git과 GitHub는 다른 것

둘은 이름이 비슷해서 자주 섞어 부르지만, 역할이 달라요. 공식 홈페이지는 Git (git-scm.com), GitHub (github.com), GitHub Docs (한국어)예요.

Git (깃)

파일의 변경 기록을 남기는 버전 관리 도구예요. 내 컴퓨터 안에서 동작하고, 인터넷이 없어도 쓸 수 있어요. 2005년 리눅스 개발자 리누스 토르발스가 만들었어요.

vs
GitHub (깃허브)

Git으로 관리하는 프로젝트를 인터넷에 올려 두고 함께 일하는 서비스예요. 보관, 공유, 리뷰, 이슈 관리, 배포까지 협업 기능을 더해 줘요.

비유하면 Git은 문서 프로그램의 "버전 기록" 기능, GitHub는 그 문서를 올려 두고 팀이 함께 댓글 달고 승인하는 공유 드라이브예요. 오늘은 설치 없이 GitHub 웹 화면만으로 Git의 핵심 동작을 해 봐요.

오늘 쓰지 않는 것
GitHub를 검색하면 "Git 명령어", "터미널", "설치" 같은 말이 많이 나와요. 이것은 개발자가 자기 컴퓨터에서 Git을 쓰는 방법이에요. 클로드 코드 같은 AI 코딩 도구는 이 Git 명령어를 대신 실행해 줘요. 명령어를 외울 필요는 없지만, "커밋해 줘", "푸시해 줘", "이 커밋으로 되돌려 줘"가 무슨 뜻인지 알아야 AI에게 정확히 시키고 결과를 확인할 수 있어요. 오늘은 브라우저 화면만 쓰고, 설치가 필요한 동작은 뜻만 알아 둬요.

GitHub는 누가 만들고, 누가 샀고, 지금 어떻게 바뀌고 있나요?

GitHub 로고와 화면 곳곳에 나오는 고양이 머리에 문어 다리를 단 캐릭터가 옥토캣(Octocat)이에요. 이름도 "문어(Octopus) + 고양이(Cat)"예요. GitHub를 상징하는 캐릭터예요.

  • 원래 이름은 "Octopuss". 일러스트레이터 사이먼 옥슬리(Simon Oxley)가 2007년에 그려 올린 이미지예요. GitHub 창업자들이 404(페이지 없음) 화면에 쓸 그림을 찾다가 이 그림을 발견해 "Octocat"으로 이름을 바꾸고, 독점 사용권을 협상해 얻었어요.
  • 같은 작가가 트위터의 첫 파랑새도 그렸어요. 2006년 스톡 이미지 사이트(iStockphoto)에 올린 새 그림을 트위터 창업자들이 10~15달러에 샀고, 작가는 수수료를 빼고 약 2~6달러를 받았다고 해요. 작가는 2009년 CNN 방송에서 자기 새를 보고서야 알았대요.
  • 옥토캣은 말을 하지 않아요. 2011년부터 캐릭터를 다듬은 GitHub 디자이너 캐머런 맥피(Cameron McEfee)는 "옥토캣은 말하지 않고, 상황·행동·표정으로만 감정을 보여 준다"는 규칙을 두었다고 밝혔어요. 지금까지 나온 다양한 옥토캣 그림은 Octodex에서 볼 수 있어요. 캐릭터의 이름은 "모나(Mona)"예요.

1-8. 오늘의 용어 지도

오늘 나오는 GitHub 용어는 아래가 전부예요. 지금 다 외우지 않아도, 실습하면서 다시 돌아와 확인하면 돼요.

REPOSITORY

저장소

프로젝트 파일과 그 변경 기록을 모아 두는 폴더.

COMMIT

커밋

변경 내용을 메모와 함께 기록하는 것. 커밋한 시점으로 언제든 돌아갈 수 있어요.

BRANCH

브랜치

원본을 건드리지 않고 따로 작업하는 갈래. 기본 갈래 이름은 main이에요.

REMOTE / LOCAL

원격 / 로컬

원격은 GitHub에 있는 저장소, 로컬은 내 컴퓨터(또는 AI 작업 공간)에 있는 복사본이에요.

PUSH / PULL / CLONE

푸시 / 풀 / 클론

푸시는 로컬 → 원격으로 올리기, 풀은 원격 → 로컬로 최신 받기, 클론은 원격 저장소를 기록째 처음 복사해 오기예요.

PULL REQUEST

풀 리퀘스트(PR)

"내 브랜치의 변경을 main에 합쳐 주세요"라는 요청. 여기서 검토와 의견이 오가요.

MERGE

병합

브랜치의 변경을 다른 브랜치에 합치는 것. 같은 줄을 서로 다르게 고쳤으면 충돌(conflict)이 나요.

ISSUE

이슈

할 일, 버그, 요청을 적어 두는 게시글. 담당자를 정하고 PR과 연결할 수 있어요.

RELEASE

릴리스

"이 시점이 v1.0이에요"처럼 특정 커밋에 이름표(태그)를 달아 공개하는 것이에요.

GitHub는 계정을 만들자마자 2단계 인증을 요구하지 않아요. 코드를 올리는 등 활동을 한 계정을 골라 안내 메일을 보내고, 그때부터 45일 안에 설정하게 해요(아래 "의무 정책" 참고). 수업 시간이 부족하면 이 칸은 건너뛰고 세션 3으로 가세요. 건너뛴 사람은 오늘 수업이 끝난 뒤 아래 순서대로 설정해 두면 돼요.

① 먼저 휴대폰에 인증 앱 설치하기

2단계 인증의 첫 준비물은 휴대폰의 인증 앱이에요. 아래 둘 중 하나를 휴대폰 앱 스토어(아이폰은 App Store, 안드로이드는 Google Play)에서 이름으로 검색해 설치해요. 둘 다 무료예요. 이미 쓰는 인증 앱(예: 1Password)이 있으면 그 앱을 써도 돼요.

"GitHub" 앱(GitHub Mobile)을 받는 게 아니에요. GitHub Mobile은 인증 앱을 먼저 연결한 뒤에 추가로 쓸 수 있어요. 처음 설정에는 위 인증 앱이 필요해요.

② 2단계 인증이 뭔지 알고 GitHub에서 켜기

2단계 인증(2FA, Two-Factor Authentication)은 비밀번호에 더해 휴대폰 인증 앱의 숫자 같은 두 번째 확인을 거쳐야 로그인되게 하는 방법이에요. 비밀번호가 새어 나가도 내 계정을 지킬 수 있어요. GitHub는 계정을 만든 뒤 2단계 인증 설정을 강하게 권장해요.

GitHub의 2단계 인증 의무 정책
GitHub는 GitHub.com에서 코드를 올리는 등 기여자로 볼 수 있는 활동을 한 계정을 골라 2단계 인증을 의무로 요구해요(예: 앱·액션 공개, 릴리스 만들기). 대상이 되면 이메일과 GitHub 화면 배너로 안내를 받고, 45일 안에 설정해야 해요. 기한 뒤 유예 기간(7일)까지 설정하지 않으면 설정할 때까지 GitHub.com을 쓸 수 없어요. 안내를 받지 않았다면 지금 의무는 아니지만, 시간이 되면 미리 설정해 두는 것을 권해요.
"휴대폰 인증 앱"이 뭔가요? GitHub 앱을 받으라는 건가요?
아니에요. 여기서 말하는 인증 앱은 30초마다 바뀌는 6자리 숫자를 만들어 주는 앱(TOTP 앱)이에요. 휴대폰 앱 스토어에서 받는 Google Authenticator나 Microsoft Authenticator 같은 앱이 대표적이에요. GitHub 공식 문서는 특정 앱을 정해 두지 않고, 원하는 TOTP 앱을 쓰면 된다고 안내해요.

README.md는 저장소에 들어온 사람이 가장 먼저 보는 소개 글이에요. 이름 끝의 .md는 Markdown(마크다운) 형식이라는 뜻이에요. 마크다운은 간단한 기호로 제목·목록·굵은 글씨를 만드는 글쓰기 방법이에요. GitHub는 .md 파일을 열면 기호 대신 꾸며진 모양으로 보여 줘요.

3-7. 원격과 로컬: 파일은 두 곳에 있어요

3-6까지는 GitHub 웹 화면 안에서 바로 고쳤어요. 하지만 실제로 AI와 일할 때는 파일이 두 곳에 있어요. 이 두 곳을 구분하는 말이 원격과 로컬이에요.

GitHub에 있는 저장소예요. 모두가 함께 보는 공식 보관함이에요. 예: github.com/내아이디/my-first-site

용어뜻업무로 비유하면
클론 (Clone)원격 저장소를 기록째 로컬로 처음 복사해 오는 것공유 폴더를 통째로 내 컴퓨터에 받아 오기
커밋 (Commit)로컬에서 고친 내용을 메모와 함께 기록하는 것v02로 저장하고 변경 이력표에 한 줄 적기

2고치기·커밋로컬에서
3푸시로컬 → 원격 브랜치로

5풀원격 최신 → 로컬

6-4. (선택) 충돌 풀기와 협업 규칙

충돌은 실수가 아니라, Git이 "두 사람이 같은 줄을 다르게 고쳤는데 어느 쪽으로 할지 사람이 정해 주세요"라고 묻는 상황이에요. 시간이 남는 짝은 아래를 펼쳐 직접 겪어 봐요.

(선택) 실습: 같은 줄을 동시에 고쳐 충돌 만들고 풀기눌러서 펼쳐 보세요
A와 B 동시에: 각자 새 브랜치(fix/title-a, fix/title-b)에서 sale.html의 <h1> 제목을 서로 다른 문구로 바꾸고 PR을 하나씩 만들어요. (A: 주말 한정 특가, B: 이번 주만 특가)
A: A의 PR을 먼저 병합해요.
B의 PR 화면: 충돌 때문에 바로 병합할 수 없다는 안내와 [Resolve conflicts] 버튼이 보이는지 확인해요.
B: [Resolve conflicts]를 누르면 두 문구가 표시 줄과 함께 보여요. 둘 중 하나(또는 합친 문구)만 남기고 표시 줄을 지운 뒤 [Mark as resolved] → [Commit merge]를 눌러요.
A: 충돌이 풀린 PR을 리뷰하고 병합해요.
충돌 화면에서 보이는 표시 예시
<<<<<<< fix/title-b
  <h1>이번 주만 특가</h1>
=======
  <h1>주말 한정 특가</h1>
>>>>>>> main

위쪽(<<<<<<< 부터 ======= 까지)은 내 브랜치 내용, 아래쪽(======= 부터 >>>>>>> 까지)은 합치려는 쪽 내용이에요. 표시 줄 세 개(<<<, ===, >>>)는 반드시 지워야 해요.

웹에서 풀 수 있는 충돌은 간단한 것뿐이에요
GitHub 웹에서는 줄 내용이 서로 다른 간단한 충돌만 풀 수 있고, 그 밖의 충돌은 명령줄에서 풀어야 해요. [Resolve conflicts] 버튼이 비활성화되어 있으면 AI 코딩 도구에게 "충돌 파일과 양쪽 내용을 보여 주고, 어느 쪽을 남길지 나에게 물어본 뒤 해결해 줘"라고 요청해요. 어느 쪽을 남길지는 요구사항을 아는 사람이 정해야 해요.

6-5. 상용화를 위한 개발·운영 관리 한눈에 보기

실제 사용자가 쓰는 서비스가 되면 "고치는 곳"과 "사용자가 보는 곳"을 나눠야 해요. 실험 중인 기능, 아직 리뷰하지 않은 문구, AI가 잘못 바꾼 코드가 그대로 사용자에게 보이면 안 되기 때문이에요. 오늘은 PM이 개발팀과 출시 방식을 정할 때 쓰는 말의 뜻만 알아 둬요.

장치한 줄 풀이
환경 나누기로컬(작업하는 나) → 미리보기·스테이징(팀·PM·QA 확인) → 운영(실제 사용자)으로 나눠, 검증을 마친 것만 공개해요.
브랜치 전략main을 운영으로 두고 기능 브랜치를 PR로 합치거나, main·develop·기능 브랜치로 한 단계 더 나눠요.
브랜치 보호 규칙"main 직접 커밋 금지", "승인 1명 이상"을 설정으로 강제해요. 무료 요금제에서는 공개 저장소에서만 쓸 수 있어요.
배포 연결main이 바뀌면 웹사이트가 따라 바뀌게 연결해요. my-first-site도 나중에 GitHub Pages로 이렇게 공개해요.
릴리스와 롤백(Rollback)출시 시점마다 버전 이름표(v1.0.0)를 달고, 문제가 생기면 원인 PR을 [Revert]로 되돌려요.
비밀 정보 관리API 키 같은 값은 저장소 밖(Secrets, 배포 서비스 환경 변수)에 두고, .gitignore로 커밋되지 않게 막아요.
오늘 my-first-site에는 브랜치 보호 규칙을 켜지 않아요

환경누가 보나목적

브랜치 전략 두 가지

A. main + 기능 브랜치

main = 운영. 모든 작업은 feature/… 브랜치에서 하고 PR로 main에 합쳐요. PR마다 미리보기 주소로 확인해요.

소규모 팀, 자주 내보내는 웹 서비스, 바이브코딩 프로젝트에 맞아요.

vs
B. main + develop + 기능 브랜치

main = 운영, develop = 개발 통합. 기능은 develop에 먼저 모아 스테이징(Staging) 환경에서 확인한 뒤, 출시할 때 develop → main으로 합쳐요.

출시 일정이 정해져 있거나, 고객사 검수를 거쳐야 하는 프로젝트에 맞아요.

1feature/…기능 작업
2PR → develop리뷰 후 개발 통합
3스테이징 확인PM·고객사 검수
4PR → main출시 승인
5운영 배포사용자에게 공개

위 흐름은 B 전략 예시예요. A 전략은 2~3단계 없이 PR 미리보기에서 확인하고 바로 main으로 합쳐요.

B 전략에서 이슈 자동 닫힘 주의
closes #번호는 기본 브랜치(main)로 병합될 때만 동작해요. develop으로 병합하는 PR에서는 이슈가 닫히지 않으니, 출시 PR(develop → main)에 해결한 이슈 번호를 모아 적거나 직접 닫아요.

운영 브랜치 지키기 (강사 시연)

[Settings] → Code, planning, and automation 영역의 [Branches] → [Add classic branch protection rule]에서 Branch name pattern에 main을 적고, [Require a pull request before merging]과 그 아래 [Require approvals]를 켜면 승인 없이는 main에 합칠 수 없어요. 같은 일을 더 세밀하게 하는 룰셋(Rulesets)도 있고, 무료 요금제에서는 이것도 공개 저장소에서만 쓸 수 있어요.

배포와 미리보기 환경

GitHub Pages는 저장소 하나에서 운영 사이트 하나를 공개하는 구조라서, PR마다 미리보기 주소를 따로 만들지는 않아요. PR별 미리보기가 필요하면 Vercel처럼 미리보기 배포를 제공하는 서비스를 GitHub에 연결해요. Vercel은 운영 브랜치가 아닌 브랜치에 커밋하거나 PR을 만들면 미리보기 배포를 만들고, 그 주소를 PR 댓글 등으로 보여 줘요. 무료 요금제의 GitHub Pages는 공개 저장소에서만 쓸 수 있어요.

GitHub의 Environments: 저장소 [Settings] → [Environments]에서 staging, production 같은 배포 환경을 만들고, 운영 배포 전에 지정한 사람의 승인(Required reviewers)을 받게 할 수 있어요. 무료 요금제에서는 공개 저장소에서만 설정할 수 있어요. 자동 배포(GitHub Actions)와 함께 쓰는 기능이라 오늘은 개념만 알아 둬요.

릴리스와 롤백(Rollback)

운영에 내보낸 시점마다 이름표를 달아 두면, "v1.1 출시 뒤로 문의가 늘었다" 같은 이야기를 정확한 기록과 함께 할 수 있어요. 저장소 오른쪽 [Releases] → [Draft a new release]에서 [Choose a tag]에 v1.0.0을 적고, [Generate release notes]로 병합된 PR 목록을 채운 뒤 [Publish release]를 눌러요.

버전 번호 관례: v주.부.수(예: v1.0.0 → 기능 추가는 v1.1.0, 작은 수정은 v1.0.1) 형식을 많이 써요. GitHub가 강제하는 규칙은 아니고 널리 쓰이는 관례(시맨틱 버저닝, Semantic Versioning)예요.

롤백(Rollback): 출시 뒤 문제가 생기면, 원인이 된 PR을 3-6의 [Revert]로 되돌리고 병합해요. main이 바뀌면 배포도 따라 바뀌어요. 원인 파악은 그 다음에 해요. 되돌림 PR도 기록으로 남아요.

비밀 정보 관리

상용 서비스에는 API 키, 결제 키, 데이터베이스 주소 같은 비밀 정보가 들어가요. 이것이 저장소에 올라가면 공개 저장소에서는 누구나 볼 수 있고, 지운 뒤에도 커밋 기록에 남아요.

장치무엇을 하나
.gitignore커밋하지 않을 파일 목록. 비밀 정보를 담은 설정 파일(예: .env)을 여기에 적어 Git이 아예 기록하지 않게 해요. 저장소를 만들 때 함께 만들 수 있어요.
Secrets[Settings] → Security 영역의 [Secrets and variables] → [Actions]에 비밀 값을 저장하고, 자동 배포(GitHub Actions)에서 이름으로만 불러 써요. 값은 화면에 다시 보이지 않아요.

오늘 정리와 과제

  • 버전 관리는 업무에서 이미 하던 일이에요. 파일 이름 대신 GitHub의 커밋이 누가·언제·무엇을 바꿨는지 기록해 줘요.
  • 우리가 GitHub를 쓰는 핵심 이유는 내 파일을 올리고 내리기 위해서예요. 원격은 GitHub, 로컬은 실제로 고치는 작업 공간이에요.
  • 푸시(올리기)·풀(받아 오기)은 뜻만 알고, 1인 바이브코더는 Claude에게 말로 시키고 GitHub에서 확인해요.
  • 혼자여도 브랜치 → PR → [Files changed] 확인 → 병합을 거치면 AI가 바꾼 것을 합치기 전에 볼 수 있어요.
  • Public 저장소의 index.html은 GitHub Pages로 누구나 여는 주소가 돼요. 공개되니 개인정보는 넣지 않아요.
  • 제품은 문제 발견 → 기획 → 디자인 → 개발 → 테스트 → 출시 → 측정·개선을 돌며 만들어져요. 한 번에 쭉 가면 폭포수, 작게 여러 번 돌면 애자일이에요.
