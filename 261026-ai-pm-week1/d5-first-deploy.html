SESSION 1 · 09:00–10:00

오늘의 지도와 화면 기획

집을 지을 때 설계도를 먼저 그리듯, 웹페이지도 무엇을 어떤 순서로 보여 줄지 먼저 정해요. 기획이 분명할수록 AI도 원하는 결과를 더 잘 만들어요.

1-1. 오늘 하루의 흐름

1기획종이에 섹션 그리기
2만들기AI 채팅으로 index.html
3확인·수정브라우저로 열고 하나씩 고치기
4올리기GitHub 저장소에 커밋
5배포GitHub Pages 주소로 열기

DAY 4에 배운 것과 이어져요. 메모장으로 저장한 .html 파일은 내 컴퓨터에서만 열렸어요. 오늘은 그 파일을 GitHub에 올려서 인터넷 주소로 누구나 열 수 있게 만들어요. 이렇게 만든 결과물을 사람들이 볼 수 있는 곳에 내보내는 일을 배포(Deployment)라고 해요.

용어한 줄 풀이
index.html웹사이트 주소로 들어왔을 때 가장 먼저 보여 주는 첫 화면 파일 이름이에요.
섹션(section)페이지를 내용별로 나눈 덩어리예요. 예: 소개, 경력, 연락 방법
커밋(commit)파일을 바꾼 내용을 저장소에 "저장 기록"으로 남기는 일이에요. DAY 3에 README를 고칠 때 해 봤어요.
배포(Deployment)만든 결과물을 인터넷에 올려 다른 사람이 주소로 볼 수 있게 하는 일이에요.

1-2. 내 페이지에 들어갈 재료 모으기

DAY 1에 만든 성장 로드맵에서 아래 재료를 메모장에 옮겨 적어요. 내가 실제로 겪은 일만 적어요.

재료어디서 가져오나요예시(가상 인물 김셀렉)
한 줄 소개성장 로드맵의 결과 이미지 두 문장"현장의 불편을 서비스로 바꾸는 예비 서비스 기획자"
해 온 일DAY 1 3문장 자기소개 ①"생활용품 매장에서 12년 동안 고객 응대와 재고 관리"
경력에서 찾은 불편DAY 1 3문장 자기소개 ②"같은 재입고 문의에 하루 수십 번 답했어요"
이 과정에서 만들 것성장 로드맵의 결과 이미지"재입고 알림 신청 웹 서비스를 기획하고 배포"
연락 방법내 GitHub 주소https://github.com/[내 GitHub 아이디]

1-3. 종이에 화면 그리기

실습 종이 한 장(또는 메모장)에 위에서 아래로 상자 4개를 그리고, 상자마다 제목과 들어갈 문장을 적어요. 이렇게 손으로 그린 간단한 화면 설계를 와이어프레임이라고 해요.

맨 위에 이름(가명 가능)과 한 줄 소개 상자를 그려요.
두 번째 상자: 소개 — 해 온 일 1~2문장
세 번째 상자: 경력에서 찾은 불편 — 불편 1~2개
네 번째 상자: 이 과정에서 만들 것 — 결과 이미지 문장
맨 아래: 연락 방법 — 이메일·전화번호 대신 GitHub 주소
다 그렸으면 사진을 찍지 않아도 괜찮아요. 상자 순서와 문장만 메모장에 옮겨 두면 다음 세션에서 그대로 써요.
  • 섹션이 3~4개로 정리되었나요?
  • 섹션마다 들어갈 문장이 내 말로 적혀 있나요?
  • 전화번호, 주소, 개인 이메일이 빠져 있나요?
SESSION 2 · 10:00–12:00

AI 채팅으로 index.html 만들기

와이어프레임을 AI 채팅에 설명해 웹페이지 코드를 받고, 메모장에 저장해서 브라우저로 열어요. 코드를 외울 필요는 없어요. 요청을 정확히 하고, 결과를 확인하는 것이 우리의 일이에요.

2-1. 요청·내용·형식으로 프롬프트 쓰기

실습 아래 프롬프트를 복사해 AI 채팅에 붙이고, [ ] 부분을 1-2·1-3의 메모로 바꿔요.

프롬프트 · 복사해서 사용하세요
요청: 나를 소개하는 한 페이지짜리 포트폴리오 첫 페이지를 HTML과 CSS가 한 파일에 들어간 index.html 하나로 만들어 줘.
내용: 이름 [이름 또는 가명] / 한 줄 소개 [결과 이미지 문장] / 소개 [해 온 일 1~2문장] / 경력에서 찾은 불편 [불편 1~2개] / 이 과정에서 만들 것 [결과 이미지 문장] / 연락 방법 [https://github.com/내 GitHub 아이디]. 섹션 순서는 위에 적은 순서 그대로야.
형식: 코드 전체를 한 번에 보여 줘. 휴대폰 화면에서도 글자가 잘리지 않게 해 줘. 외부 라이브러리, 외부 글꼴, 이미지 파일은 쓰지 말아 줘. 내가 적지 않은 경력·숫자·연락처는 추가하지 말고, 비어 있는 칸은 [확인 필요]로 남겨 줘. 코드 아래에 각 부분이 무슨 역할인지 3줄로 설명해 줘.
AI 채팅마다 화면과 답이 달라요
같은 프롬프트라도 AI 채팅 종류와 그날 상황에 따라 결과 모양이 달라요. 유료 플랜도 사용 한도가 있으니, 같은 요청을 여러 번 새로 보내기보다 받은 결과를 고쳐 가며 쓰는 것이 좋아요. 답이 중간에 끊기면 "이어서 보여 줘"라고 요청해요.

2-2. AI가 만들어 줄 결과의 예시

아래는 가상 인물 "김셀렉"의 메모로 만든 결과 예시예요. 여러분의 AI 결과와 똑같지 않아도 괜찮아요. 내 결과가 이상하게 보일 때 비교용으로 열어 보세요.

HTML예시 결과: 김셀렉 소개 페이지 (index.html)HTML+CSS 한 파일 · 외부 자원 없음 · 휴대폰 화면 대응⬇ 다운로드

예시 파일의 앞부분은 이렇게 생겼어요. DAY 4에 본 것처럼 <head>에는 페이지 정보와 꾸미기(CSS), <body>에는 화면에 보이는 내용이 들어가요.

예시 코드 일부 · 읽기용
<!DOCTYPE html>
<html lang="ko">
<head>
<meta charset="UTF-8">
<meta name="viewport" content="width=device-width, initial-scale=1">
<title>김셀렉 | 포트폴리오 첫 페이지</title>
<style> ...꾸미기 규칙... </style>
</head>
<body>
  <header><h1>김셀렉</h1> ...</header>
  <main>
    <section><h2>안녕하세요</h2> ...</section>
  </main>
</body>
</html>
코드 조각역할
<meta charset="UTF-8">한글이 깨지지 않게 글자 방식을 알려 줘요.
<meta name="viewport" ...>휴대폰에서 화면 폭에 맞춰 보이게 해요.
<style>색, 글꼴 크기, 여백 같은 꾸미기 규칙(CSS)이 들어가요.
<section>1-3에서 그린 상자 하나하나예요.

2-3. 메모장에 저장하고 브라우저로 열기

DAY 4에 해 본 방법 그대로예요.

AI 답변의 코드 상자에서 복사 버튼을 누르거나, <!DOCTYPE html>부터 </html>까지 빠짐없이 드래그해 복사해요.
DAY 4에 쓴 메모장 프로그램을 새로 열고 붙여 넣어요.
파일 이름을 정확히 index.html로 정해, 준비해 둔 my-first-site 폴더에 저장해요. Windows 메모장은 저장할 때 인코딩을 UTF-8로 골라요.
저장한 파일을 더블클릭하거나 브라우저 창으로 끌어다 놓아 열어요.
브라우저 창의 폭을 좁게 줄여 휴대폰 화면처럼 만들어 보고, 글자가 잘리거나 옆으로 넘치지 않는지 봐요.
파일 이름이 index.html.txt가 되지 않았나요? 파일을 더블클릭했는데 메모장으로 열리면 이름 끝에 .txt가 붙었을 수 있어요. 파일 이름을 다시 확인하고, 막히면 채팅에 "막혔어요 2-3"을 남겨 주세요.
  • 브라우저 주소창이 file://로 시작하고 내 페이지가 보이나요?
  • 한글이 깨지지 않고 보이나요?
  • 섹션 순서가 내가 그린 와이어프레임과 같나요?
  • AI가 내가 말하지 않은 경력, 숫자, 연락처를 지어내지 않았나요? 있으면 표시해 두세요. 다음 세션에서 고쳐요.
  • [확인 필요]로 남은 칸이 있다면 메모해 두었나요?
SESSION 3 · 13:00–14:00

수정 요청 반복하기와 디자인 시스템 맛보기

AI에게 한 번에 많은 것을 고쳐 달라고 하면, 원하지 않는 곳까지 바뀌기 쉬워요. 한 번에 하나만 고치고, 고친 곳을 설명해 달라고 하면 결과를 확인하기 쉬워요.

3-1. 한 번에 하나만 고치기

실습 2-3 체크리스트에서 표시한 고칠 곳 중 하나만 골라 아래 프롬프트로 요청해요.

프롬프트 · 복사해서 사용하세요
요청: 방금 만든 index.html에서 딱 한 곳만 고쳐 줘.
내용: 고칠 곳 [예: '경력에서 찾은 불편' 섹션에 내가 말하지 않은 문장이 있어. 이 문장을 지우고 내 문장 '...'으로 바꿔 줘]. 다른 섹션의 글, 색, 순서는 그대로 둬.
형식: 고친 index.html 코드 전체를 보여 주고, 코드 아래에 어느 줄을 무엇에서 무엇으로 바꿨는지 2줄로 설명해 줘. 요청하지 않은 기능이나 꾸미기는 추가하지 마.
AI가 준 새 코드 전체를 복사해요.
메모장의 기존 내용을 모두 지우고(전체 선택 후 삭제) 새 코드를 붙여 넣은 뒤 같은 이름으로 저장해요.
브라우저에서 새로고침해 바뀐 곳을 확인해요.
AI의 설명과 실제로 바뀐 곳이 같은지 비교해요. 다르면 "설명과 다르게 ○○도 바뀌었어. 원래대로 돌려 줘"라고 요청해요.
잘 된 버전은 따로 남겨 두세요
수정하다 망가질 때를 대비해, 마음에 드는 상태가 되면 메모장에서 index_백업1.html 같은 이름으로 한 부 더 저장해 두세요. 오후에는 GitHub의 커밋 기록이 이 역할을 대신해 줘요.

3-2. 디자인 시스템이란

디자인 시스템은 색, 글꼴 크기, 여백, 버튼 모양 같은 꾸미기 규칙을 미리 정해 두고 모든 화면에서 똑같이 쓰는 약속이에요. 큰 회사는 이 약속을 문서와 부품(컴포넌트) 모음으로 관리해요. 컴포넌트는 버튼, 카드처럼 여러 화면에서 다시 쓰는 화면 부품이에요.

규칙

색

주 색 1개 + 포인트 색 1개. 예: 진한 남색(글자·배경), 주황(강조·링크)

규칙

글꼴 크기 3단계

큰 제목 32px / 섹션 제목 20px / 본문 16px. px는 화면의 점 크기 단위예요.

효과

왜 정하나요

페이지가 늘어나도 같은 서비스처럼 보이고, AI에게 수정을 맡겨도 모양이 들쭉날쭉해지지 않아요.

3-3. 내 규칙을 정해 AI에게 지키게 하기

실습 내 페이지에 쓸 색 2개와 글꼴 크기 3단계를 정하고, AI에게 이 규칙만 쓰도록 요청해요. 색 이름은 "진한 남색", "연한 회색"처럼 말로 적어도 괜찮아요.

프롬프트 · 복사해서 사용하세요
요청: index.html의 꾸미기를 아래 디자인 규칙만 쓰도록 바꿔 줘.
내용: 색은 주 색 [예: 진한 남색]과 포인트 색 [예: 주황] 두 가지만 쓰고, 배경은 흰색으로 해 줘. 글꼴 크기는 큰 제목 [32px], 섹션 제목 [20px], 본문 [16px] 세 단계만 써 줘. 이 규칙을 CSS 맨 위에 이름을 붙여 한곳에 모아 줘. 글 내용과 섹션 순서는 바꾸지 마.
형식: 고친 index.html 코드 전체와, 규칙을 모아 둔 부분이 어디인지 2줄 설명. 규칙에 없는 색이나 글꼴 크기는 추가하지 마.

예시 파일에서는 이 규칙이 :root라는 곳에 이름표를 붙여 모여 있어요. 이름표 하나만 바꾸면 페이지 전체의 색이 함께 바뀌어요.

예시 코드 일부 · 읽기용
:root { --main: #1f2a44; --point: #e8772e; --big: 32px; --mid: 20px; --base: 16px; }
  • CSS 안에 색 2개와 글꼴 크기 3개가 한곳에 모여 있나요?
  • 브라우저에서 보이는 색이 내가 정한 두 가지(와 흰 배경)뿐인가요?
  • 글 내용과 섹션 순서가 그대로인가요?
  • 창을 좁혀도 글자가 잘리지 않나요?

GitHub에 올리기: 파일 업로드와 커밋 메시지 규칙

DAY 3에 만든 my-first-site 저장소에 오늘 만든 index.html을 올려요. AI가 짠 코드도 언제, 무엇을, 왜 바꿨는지 기록으로 남겨 두면, 나중에 문제가 생겨도 이전 상태를 찾아볼 수 있어요.

4-1. 커밋 메시지 규칙: Conventional Commits

커밋 메시지는 "이번 저장에서 무엇을 했는지" 적는 한 줄 메모예요. 사람마다 제멋대로 쓰면 기록을 읽기 어려워서, 많은 팀이 Conventional Commits라는 공개 규칙을 써요. 기본 모양은 아래와 같아요.

기본 모양 · 읽기용
<type>[optional scope]: <description>

type은 변경의 종류, [optional scope]는 바꾼 범위(생략 가능), description은 짧은 설명이에요. 오늘은 scope 없이 종류: 설명만 써요.

type공식 사이트의 뜻우리 반 예시
feat새 기능을 추가하는 커밋feat: 첫 소개 페이지 추가
fix버그(잘못된 동작)를 고치는 커밋fix: 모바일에서 잘리는 제목 수정
docs 등공식 사이트는 feat·fix 외에 build, chore, ci, docs, style, refactor, perf, test 등의 종류도 쓸 수 있다고 안내하며, 이는 @commitlint/config-conventional(Angular 규칙 기반)의 권장이라고 소개해요.docs: README에 페이지 주소 추가
우리 반 약속
① 종류(type)는 영어 소문자로 쓰고, 콜론(:) 뒤에 한 칸 띄어요. ② 설명은 한국어로, 무엇을 했는지 짧게 써요. ③ 한 커밋에는 한 가지 변경만 담아요. 공식 사이트도 대소문자는 자유지만 일관되게 쓰라고 안내해요.
  • "수정", "ㅇㅇ", "final"처럼 무엇을 했는지 알 수 없는 메시지가 아닌가요?
  • type 뒤에 콜론(:)과 띄어쓰기가 있나요?

GitHub Pages로 배포하고 내 주소 열기

GitHub Pages는 GitHub 저장소에 있는 HTML 파일을 웹사이트로 보여 주는 GitHub의 기능이에요. 공식 문서에 따르면 GitHub Free 플랜에서도 Public 저장소라면 쓸 수 있어요. DAY 3에 저장소를 Public으로 만든 이유가 여기 있어요.

5-1. Pages 설정하기: Deploy from a branch

강사 시연 강사 화면으로 먼저 보고, 실습 같은 순서로 따라 해요.

my-first-site 저장소 이름 아래에 있는 [Settings]를 눌러요. [Settings]가 안 보이면 옆의 펼침 메뉴를 열고 [Settings]를 눌러요.
왼쪽 메뉴의 "Code, planning, and automation" 묶음에서 [Pages]를 눌러요.
"Build and deployment" 아래 "Source"에서 [Deploy from a branch]를 골라요.
브랜치 펼침 메뉴에서 main을 고르고, 폴더 펼침 메뉴는 /(root)로 둬요. root는 저장소의 맨 위 칸(최상단)이라는 뜻이에요.
[Save]를 눌러요.
왜 index.html을 맨 위에 두었나요?
공식 문서에 따르면 GitHub Pages는 index.html, index.md, README.md 파일을 사이트의 첫 화면(entry file)으로 찾고, 브랜치와 폴더에서 배포할 때는 이 파일이 고른 폴더의 맨 위에 있어야 해요. 우리는 /(root)를 골랐으니 index.html이 저장소 맨 위에 있어야 해요.

5-2. 내 주소 확인하고 열기

내 페이지 주소 · 복사해서 사용하세요
https://[내 GitHub 아이디].github.io/my-first-site/

[Settings] → [Pages] 화면을 다시 열어 [Visit site]가 보이면 눌러요. 또는 위 주소를 브라우저 주소창에 직접 넣어요.
휴대폰이 있다면 같은 주소를 휴대폰 브라우저로도 열어 봐요.
열린 주소를 메모장에 적어 두세요. 오늘 과제와 포트폴리오에 계속 써요.

5-4. 공개된다는 것의 의미

GitHub Pages 사이트는 인터넷에 공개돼요. 공식 문서는 GitHub Pages 사이트가 저장소가 비공개(private)이더라도 인터넷에 공개된다고 안내하고, 배포 전에 민감한 정보를 저장소에서 지우라고 해요. 우리 저장소는 Public이라 저장소 안의 파일과 커밋 기록까지 누구나 볼 수 있어요. 한번 올린 내용은 나중에 지워도 이미 누군가 봤을 수 있어요. 처음부터 개인정보·비밀번호·회사 자료는 올리지 않아요.

한 주 동안 OT, AI 특강, GitHub와 방법론, 웹의 동작 원리, 첫 배포까지 달려왔어요. DAY 3에 배운 애자일 방식처럼 한 주를 돌아보고 다음 주를 더 낫게 만들어요.

7-1. KPT란

K · Keep

계속할 것

이번 주에 잘 되어서 다음 주에도 이어 갈 것

P · Problem

문제였던 것

막히거나 아쉬웠던 것. 사람 탓이 아니라 상황과 방법을 적어요.

T · Try

시도할 것

Problem을 줄이기 위해 다음 주에 해 볼 작은 행동 1가지

7-2. 나의 KPT 적고 나누기

5분: 메모장에 K·P·T를 각각 1~2줄씩 적어요.
10분: 소회의실에서 3~4명이 돌아가며 1분씩 나눠요.
10분: 전체 방으로 돌아와 채팅에 Try 한 줄만 남겨요. 강사가 비슷한 것끼리 묶어 다음 주 월요일 그라운드 룰 돌아보기 때 함께 봐요.
마지막으로 DAY 1에 남긴 한 단어 체크인을 떠올리며, 한 주를 마친 지금의 마음을 한 단어로 채팅에 남겨요.
칸예시
Keep"막힌 지 5분 지나면 바로 채팅에 물어본 것"
Problem"AI가 준 코드를 일부만 복사해서 페이지가 깨졌다"
Try"코드를 붙여 넣은 뒤 맨 끝이 </html>로 끝나는지 먼저 보기"
  • Try가 다음 주에 바로 해 볼 수 있는 구체적인 행동인가요?
  • Problem이 사람이 아니라 상황·방법에 대한 내용인가요?
WRAP-UP

오늘 정리와 과제

  • 웹페이지는 기획(섹션 그리기) → AI로 만들기 → 확인·수정 → 올리기 → 배포 순서로 만들어요.
  • AI에게는 한 번에 하나만 고쳐 달라고 하고, 고친 곳의 설명을 받아 실제 결과와 비교해요.
  • 디자인 시스템은 색·글꼴 크기 같은 꾸미기 규칙을 정해 두고 계속 지키는 약속이에요.
  • 커밋 메시지는 feat:, fix:처럼 종류를 앞에 붙여 무엇을 했는지 한 줄로 남겨요.
  • Public 저장소와 GitHub Pages는 누구나 볼 수 있어요. 개인정보와 비밀 정보는 처음부터 올리지 않아요.
