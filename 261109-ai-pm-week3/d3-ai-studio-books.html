LLM이 무엇이고 어디서 틀리나

오늘 만드는 화면은 사용자의 감정을 AI가 읽고 책을 골라요. 먼저 그 AI, 곧 LLM이 무엇인지 알고, 책을 추천할 때 어디서 틀릴 수 있는지 직접 확인해요.

왜 하나?AI가 지어낸 책을 사용자가 사려고 누르면, 없는 상품 화면이 열려요. 기획자가 AI가 틀리는 곳을 알아야, 틀려도 사용자가 속지 않는 화면을 만들 수 있어요.

개념1-1. LLM이란?

LLM이란?

LLM(대규모 언어 모델)은 아주 많은 데이터로 학습한 언어 모델이에요. 글을 만들고, 번역하고, 요약하는 일을 해요. 클로드, 챗지피티가 모두 LLM이에요.

어떤 문제를 해결하나요?

사용자는 감정을 "설레요", "좀 지쳤어요"처럼 저마다 다르게 적어요. 규칙으로 만들면 감정 낱말마다 책 목록을 미리 짝지어 둬야 해요. LLM은 처음 보는 표현도 뜻을 읽고 어울리는 답을 글로 만들어 줘요.

조심할 점

LLM은 사실과 다르거나 주어진 내용과 맞지 않는 글을 만들 수 있어요. 이것을 환각이라고 해요. 책 추천에서는 이런 모양으로 나타날 수 있어요.

틀릴 수 있는 곳예사용자에게 생기는 일
없는 책그럴듯한 제목을 지어냄검색해도 나오지 않아요
저자 바꿔 쓰기있는 책에 다른 저자 이름을 붙임다른 책을 사게 돼요
링크 지어내기상품 번호를 지어낸 주소없는 화면이나 엉뚱한 상품이 열려요

공식 문서는 환각을 줄이는 방법으로 "모르면 모른다고 말해도 된다고 허락하기", "근거를 함께 내게 하기"를 들어요. 5세션과 6세션에서 이 방법을 기획서에 써요.

개념2-1. 웹 페이지에 AI를 붙이는 세 가지 길

최소한의 웹 페이지에 AI를 붙이는 방법은 여러 가지예요. 오늘은 세 번째 길, 클로드 아티팩트의 내장 AI로 해요.

길하는 방법
구글 AI 스튜디오지난주 금요일에 Hello 페이지를 만들었던 도구로 이어서 만들어요.

클로드 아티팩트 내장 AI클로드 유료 요금제에서 아티팩트 안에 클로드를 불러 쓰는 기능으로 만들어요.

아티팩트 내장 AI란?

아티팩트는 클로드가 대화 옆에 만들어 주는 작은 웹 페이지예요. 이 페이지 안에서 클로드를 불러 답을 받을 수 있어요. 그래서 따로 서버를 만들지 않아도 "AI가 답하는 화면"을 바로 만들어 볼 수 있어요.

어떤 문제를 해결하나요?

원래 웹 페이지에 AI를 붙이려면 API 키를 받고, 키를 숨길 서버를 만들고, 사용 요금을 내야 해요. 아티팩트 내장 AI는 API 키가 필요 없어요. 만든 사람에게 요금이 들지도 않아요.

조심할 점

  • 아티팩트를 쓰는 사람은 자기 클로드 계정으로 로그인해서 써요. 사용량은 만든 사람이 아니라 쓰는 사람의 요금제 한도에서 빠져요.
  • 새 아티팩트가 처음 클로드를 부를 때 권한을 묻는 창이 떠요. 허락해야 AI 탭이 동작해요.

API 키는 왜 서버에 두나요?

API 키는 내 계정으로 AI를 부르는 비밀 열쇠예요. 화면 코드에 넣으면 앱을 연 사람 누구나 키를 볼 수 있어요. 구글 AI 스튜디오는 키를 [Settings]의 Secrets에 넣고, 서버 쪽 코드가 그 키를 읽게 해요. 그래서 키가 브라우저에 드러나지 않아요.

  • 키를 지우면 그 키로는 더 이상 클로드를 부를 수 없어요. 그래서 수업용 키를 넣은 앱의 AI 기능은 수업 뒤에 멈춰요.

JSON이 필요한 때: 서비스 안에서 코드가 AI의 답을 읽을 때
우리 책 추천 화면은 사용자가 버튼을 누를 때마다 AI의 답을 코드가 받아서, 책 제목은 제목 칸에, 저자는 저자 칸에 나눠 넣어요. AI가 "첫 번째로 추천할 책은 ○○이고, 저자는…"처럼 긴 글로 답하면, 코드는 어디까지가 제목인지 알 수 없어요. JSON은 칸 이름(title, author, reason)이 붙어 있어서, 코드가 칸마다 정확히 꺼낼 수 있어요.

JSON이 필요 없는 때: 기획자가 요구사항을 전달할 때
기획자가 개발자에게 요구사항을 줄 때, 또는 클로드에게 "이렇게 고쳐 줘"라고 개선을 요청할 때는 자연어나 표로 충분해요. 받는 쪽이 사람(개발자)이거나 뜻을 읽을 수 있는 AI이기 때문이에요. 이 요구사항을 JSON 코드로 바꾸는 일은 구현하는 쪽이 해요.

상황누가 누구에게알맞은 모양
사용자가 버튼을 누를 때마다 AI가 답하고, 코드가 그 답을 카드에 넣음AI → 코드JSON처럼 칸이 정해진 모양
기획자가 개발자에게 요구사항을 줌기획자 → 개발자자연어, 표
기획자가 클로드에게 프로토타입 개선을 요청함기획자 → AI자연어, 표

그래서 5-2 기획서에서는 "받을 답의 모양"을 칸 이름 · 뜻 · 예로 된 표로 적어요. JSON 문법을 몰라도 괜찮아요. 5-3에서 클로드(개발자 역할)가 이 표를 보고 JSON으로 바꿔 코드에 넣어요.

JSON으로 안 받으면 생기는 일 (서비스 안에서)

  • 카드에 { } 같은 글자가 그대로 보이거나, 카드가 아예 나오지 않아요.
  • 어떤 때는 제목 칸에 저자 이름이 들어가요.

JSON으로 달라고 해도 깨질 수 있어요
공식 문서는 프롬프트로만 JSON을 달라고 하면 모양이 틀린 JSON이 나오거나 칸이 빠질 수 있다고 설명해요. 그래서 실제 서비스에서는 API의 '구조화된 출력(Structured outputs)' 기능으로 정해진 모양만 나오게 막기도 해요. 오늘은 5-4에서 "카드가 매번 제대로 나오는지"를 직접 확인해요.

JSON 말고 다른 방법도 있어요
클로드 공식 문서는 프롬프트 안의 내용을 <지시>, <입력>, <책목록>처럼 XML 태그로 나누라고 권해요. 답도 <답> 같은 태그 안에 넣으라고 할 수 있어요. 다만 오늘처럼 칸이 여러 개인 답을 코드가 나눠 담을 때는 JSON이 가장 흔히 쓰여요.

근거를 주고 추천하기 (RAG 맛보기)

이 세션은 시간이 남을 때 하는 선택 실습이에요. 화요일에 모은 책 목록을 AI에게 함께 주고, 그 안에서만 고르게 해요. 기획자가 근거 추천 기획서를 쓰고, 개발자 입장에서 목록을 붙인 뒤, 기획자가 5세션 결과와 견줘요.

왜 하나?5세션에서 프롬프트를 잘 써도 지어낸 책이 남을 수 있었어요. AI가 무엇을 근거로 답할지까지 정하는 것이 기획자의 일이에요.

개념6-1. RAG란?

RAG(검색 증강 생성)란?

RAG는 AI에게 질문만 주지 않고, 답의 근거가 될 자료를 찾아 함께 주는 방법이에요. AI는 그 자료를 보고 답해요.

어떤 문제를 해결하나요?

AI가 기억만으로 고르면 없는 책을 지어낼 수 있어요. 실제 책 목록을 주고 "이 안에서만 골라"라고 하면, 목록에 없는 책은 나오기 어려워요. 링크도 AI가 만들지 않고, 목록에 있는 실제 주소를 그대로 써요.

기억으로 추천 (5세션)목록을 주고 추천 (5세션)
책을 고르는 곳AI가 학습한 기억우리가 준 책 목록

조심할 점

  • 오늘은 목록을 통째로 넣는 맛보기예요. 실제 서비스의 RAG는 책이 수만 권이라, 질문에 맞는 책을 먼저 검색해서 일부만 AI에게 줘요.
  • 목록이 길수록 AI에게 보내는 글이 길어지고, 사용량도 많이 써요. 그래서 오늘은 목록을 100줄로 줄여서 써요.

오늘의 규칙

  • LLM은 없는 책·저자·링크를 그럴듯하게 지어낼 수 있다
  • 기획자는 요구사항을 입력·처리·출력의 기준으로 준다. 자연어와 표로 충분하다
  • 기획자는 "무엇을, 어떤 기준으로" 넘기고, 구현은 기획서에 있는 것만 만든다. 확인은 다시 기획자가 기획서의 완료 기준으로 한다
  • 서비스 안에서 코드가 AI의 답을 읽을 때는 JSON처럼 칸을 정해 받는다
  • API 키는 서버(Secrets)에만 두고 화면 코드에 두지 않는다. 다른 사람과 나누지 않는다
  • 모델은 화면이 아니라 같은 입력으로 테스트한 결과로 고른다
  • 프롬프트는 답의 모양을 좋게 하고, 근거 목록(RAG)은 지어낸 답을 막는다
  • 개수를 채우는 것보다 진짜인 것이 중요하면, "확실한 만큼만 답해도 돼"라고 허락한다
