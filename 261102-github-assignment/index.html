학생 과제를 GitHub로 받고, PR로 함께 고쳐요

학생이 매일 만든 결과물을 하나의 과제 저장소에 올리게 하는 방법을 정리해요. 학생은 브라우저에서 직접 올리는 방식과 Claude Code로 올리고 내리는 방식 두 가지로 연습하고, 팀별 폴더에서 충돌 상황을 일부러 만들어 본 뒤 강사가 해결하는 과정까지 함께 봐요.

대상과제 저장소를 운영하는 강사 (학생은 코딩 경험 없는 PM·기획자)
학생 도구GitHub 무료 계정. 방식 ①은 웹 브라우저, 방식 ②는 Claude Code(유료 요금제)
결과물과제 저장소 1개 (개인 제출 폴더 + 팀별 실습 폴더) 와 팀별 PR·충돌 해결 기록
OVERVIEW

한눈에 보기

강사 계정에 과제 저장소를 하나 만들고 학생을 협업자로 초대해요. 학생마다 자기 이름 파일만 올리고 고치면 PR끼리 충돌하지 않아요. 충돌은 팀 실습에서 일부러 만들어 보고, 해결은 강사가 시연해요.

구분내용비용
기본 학생이 GitHub에 직접 올리고 내리기방식 ① 브라우저 업로드, 방식 ② Claude Code. 바로 운영할 수 있어요.비공개 저장소 + 무료 플랜으로 0원
팀 실습 충돌 일부러 만들기강사 저장소 안에 팀별 폴더를 만들고 케이스 A·B·C를 재현한 뒤 강사가 풀어요.0원
응용 제출 페이지 → PR로 쌓기GitHub Pages만으로는 안 되고, 열쇠(토큰)를 숨기는 중계 서버(구글 Apps Script)가 있어야 해요.0원 (설계안, 수업 전 테스트 필요)
충돌은 언제 생기나
GitHub 공식 문서 기준으로 충돌은 서로 다른 변경이 같은 파일의 같은 줄을 다르게 고쳤을 때, 또는 한쪽이 고친 파일을 다른 쪽이 지웠을 때 생겨요. 같은 폴더 안이라도 파일이 다르면 충돌하지 않아요.
PART 1

공개 저장소와 비공개 저장소

공개 저장소는 누구나 볼 수 있는 게시판이지, 누구나 쓸 수 있는 게시판은 아니에요. 어느 쪽이든 파일을 올리려면 저장소 주인이 쓰기 권한을 줘야 해요.

1-1. 무엇이 다른가

항목공개 + 무료비공개 + 무료비공개 + 유료 (Pro·Team)
누가 볼 수 있나인터넷의 누구나초대받은 사람만초대받은 사람만
학생 초대 후 push가능가능 (협업자 인원 제한 없음)가능
보호 규칙 (Ruleset): 강제 덮어쓰기·브랜치 삭제 막기가능불가가능
GitHub Pages (HTML을 웹 주소로 보기)가능불가가능
비용0원0원Team: 사용자 1명당 월 4달러 (원화는 결제 시점 환율 기준). Pro 가격은 가격 페이지에 표시되지 않아 결제 전 확인

1-2. 우리 과정은 무엇을 고를까

이런 경우선택
학생 이름과 과제가 외부에 보이면 안 된다비공개 + 무료
학생끼리 결과물을 참고하고, HTML 과제를 웹 주소로 바로 열어 봐야 한다공개 + 무료
비공개이면서 보호 규칙과 Pages가 모두 필요하다유료 플랜
공개 저장소로 운영할 때
학생 실명·이메일과 API 키가 그대로 공개될 수 있어요. 폴더 이름은 영문 이름이나 닉네임으로 정하고, 개인정보 기준은 과정 주관사와 먼저 확인해요.
PART 2

강사 계정에서 과제 저장소 준비하기

과정 시작 전에 한 번 해 두는 일이에요. 학생 실습 날에는 초대 수락만 확인하면 돼요.

2-1. 저장소 만들기와 기본 파일

STEP 1. 저장소 만들기

GitHub 오른쪽 위 [+] → [New repository]를 눌러요.
Repository name에 aipm-2026-assignments처럼 과정·연도가 보이는 이름을 적어요.
1-2 기준으로 [Public] 또는 [Private]를 고르고, README 추가를 켠 뒤 [Create repository]를 눌러요.

STEP 2. README와 .gitignore 만들기

README에는 제출 규칙을, .gitignore에는 올라가면 안 되는 파일을 적어요. API 키가 공개되는 사고를 막는 가장 확실한 장치예요.

README.md · 제출 규칙 예시
# AI PM 과정 과제 저장소

## 제출 규칙
- 내 폴더(submissions/영문이름/)와 내 파일만 올리고 고친다.
- 파일·폴더 이름은 영문 소문자, 숫자, 하이픈(-)만 쓴다.
- 커밋 메시지: [영문이름] 11/03 과제 제출
- 마감: 당일 23:59 (KST)
- 다른 사람 파일은 고치거나 지우지 않는다.
- API 키, 비밀번호, .env 파일은 올리지 않는다.
.gitignore · 예시
.env
*.key
node_modules/
.DS_Store

2-2. 폴더 구조: 개인 제출과 팀 실습

개인 과제는 학생 → 날짜 순서로, 팀 실습은 팀 → 학생 파일과 팀 공용 파일로 나눠요. 이 구조만 지키면 평소 제출에서는 충돌이 생기지 않아요.

저장소 폴더 구조
aipm-2026-assignments/
├─ README.md
├─ .gitignore
├─ submissions/            ← 개인 과제
│  ├─ kim-minji/
│  │  └─ 2026-11-03/
│  │     ├─ index.html
│  │     └─ README.md      (오늘 한 일 3줄)
│  └─ lee-jun/
│     └─ 2026-11-03/
└─ teams/                  ← 팀 실습 (PART 5)
   ├─ team-1/
   │  ├─ README.md         ← 팀 공용 파일 (케이스 C용)
   │  ├─ kim-minji.md
   │  └─ lee-jun.md
   └─ team-2/
  • 폴더 이름에 한글·띄어쓰기·대문자가 없나요? (주소가 깨지거나 대소문자 때문에 못 찾는 원인이 돼요)
  • 학생별 폴더 이름을 명단과 함께 README에 적어 두었나요?
(참고) 빈 폴더는 GitHub에 만들어지지 않아요눌러서 펼쳐 보세요

Git은 파일만 기록해요. 팀 폴더를 미리 만들어 두려면 [Add file] → [Create new file]에서 파일 이름 칸에 teams/team-1/README.md처럼 슬래시(/)를 넣어 파일과 폴더를 함께 만들어요.

2-3. 학생 초대하기

학생 GitHub 아이디를 설문으로 미리 받아요.
저장소 [Settings] → 왼쪽 Access 영역의 [Collaborators] → [Add people]에서 아이디를 검색해 초대해요.
학생은 가입 이메일이나 GitHub 알림에서 초대를 수락해요. 수락해야 push할 수 있어요.

개인 계정 저장소의 협업자는 읽기와 쓰기(push) 권한을 함께 받아요. 그래서 학생 누구나 다른 학생 파일을 고칠 수 있다는 점을 첫날 분명히 알려요.

  • [Collaborators] 목록에서 학생마다 대기(Pending)가 아니라 수락 상태인가요?
GitHub Docs · 2026-10-26 확인Inviting collaborators to a personal repository

2-4. 보호 규칙과 운영 약속

저장소강사가 할 일
공개 + 무료[Settings] → [Rules] → [Rulesets]에서 main 브랜치에 강제 push 금지와 삭제 금지를 걸어요.
비공개 + 무료보호 규칙을 쓸 수 없어요. 수업에서 강제 push(force push)를 가르치지 않고, Claude Code에게도 "강제 push는 하지 마"를 프롬프트에 넣게 해요.
지워져도 되살릴 수 있어요
Git은 커밋 기록이 남기 때문에 다른 학생 파일이 실수로 바뀌거나 지워져도 이전 커밋에서 되살릴 수 있어요. 기록 자체를 지우는 강제 push만 막으면 돼요.
PART 3

학생 방식 ① 브라우저에서 직접 올리기

설치 없이 GitHub 웹 화면만 써요. 첫 제출과 Git이 처음인 학생에게 맞아요. 화면 캡처와 버튼 위치는 GitHub 기초 교안 3-2와 같아요.

3-1. 내 폴더에 파일 추가하기

STEP 1. 내 폴더로 이동하기

과제 저장소에서 submissions → 내 이름 폴더를 눌러 들어가요.
오늘 날짜 폴더가 없으면 [Add file] → [Create new file]에서 파일 이름 칸에 2026-11-03/README.md를 적어 폴더와 파일을 함께 만들어요.

STEP 2. 파일 올리기

날짜 폴더 안에서 [Add file] → [Upload files]를 눌러요.
파일을 끌어다 놓고, Commit message에 [kim-minji] 11/03 과제 제출을 적어요.
main에 바로 커밋하는 선택지를 그대로 두고 [Commit changes]를 눌러요.
브라우저로 올릴 수 있는 크기
브라우저 업로드는 파일 하나당 25MiB까지예요. Git으로 올려도 100MiB가 넘는 파일은 GitHub가 받지 않아요.
  • 올린 파일이 내 이름 폴더 안에 있나요? (저장소 맨 위에 올라가지 않았나요?)
  • 파일 목록 옆에 내 커밋 메시지가 보이나요?

3-2. 내 파일만 고치기

내 폴더의 파일을 열고 연필 버튼(편집)을 눌러요.
고친 뒤 [Commit changes...]에서 무엇을 고쳤는지 한 줄로 적고 커밋해요.
다른 학생 폴더의 파일은 열어 보기만 하고 편집하지 않아요.
  • 커밋 화면(History)에서 내 파일만 바뀌었나요?

3-3. PR로 올리고 병합 기다리기

PR을 연습하는 날에는 main에 바로 커밋하지 않고 브랜치를 만들어 PR로 올려요. 팀 실습(PART 5)도 이 방법으로 해요.

업로드나 편집 뒤 커밋 창에서 새 브랜치를 만드는 선택지를 골라요. 브랜치 이름은 submit/kim-minji-1103처럼 이름과 날짜를 넣어요.
PR 작성 화면에서 제목을 [kim-minji] 11/03 과제로 적고 [Create pull request]를 눌러요.
강사나 팀원이 리뷰하고 [Merge pull request]로 합쳐요.
PR은 한 사람당 한 번에 하나
같은 파일을 고치는 PR을 두 개 열면 케이스 A 충돌이 생겨요. 고칠 게 더 있으면 새 PR을 열지 말고, 같은 브랜치에 커밋을 더하면 기존 PR에 자동으로 붙어요.
PART 4

학생 방식 ② Claude Code로 올리고 내리기

과제 저장소를 내 컴퓨터(로컬)에 복사해 두고, Claude Code 채팅으로 고치고 올리고 내려받아요. 명령어를 외우지 않고 말로 시키되, 결과는 GitHub 화면에서 확인해요.

4-1. 준비물과 연결 확인

준비물확인 방법
Claude Code (유료 요금제)설치와 로그인은 Claude Code 공식 빠른 시작 문서를 따라요.
Git과 GitHub 로그인아래 프롬프트로 Claude Code에게 직접 확인시켜요.
과제 저장소 협업자 초대 수락2-3의 체크리스트
Claude Code 프롬프트 · 연결 확인
요청: 이 컴퓨터에서 Git과 GitHub를 쓸 준비가 됐는지 확인해 줘.
내용: Git이 설치돼 있는지, GitHub에 내 계정으로 로그인돼 있는지 실제 명령으로 확인해. 안 돼 있으면 설치·로그인 방법을 한 단계씩 알려 주고, 내가 브라우저에서 해야 하는 일은 멈추고 기다려. 비밀번호나 토큰을 채팅에 붙여 넣으라고 하지 마.
형식: 항목별 준비됨/안 됨 표와, 안 된 항목의 다음 할 일.
Claude Code DocsQuickstart

4-2. 저장소를 내 컴퓨터로 클론하기

클론(Clone)은 원격 저장소를 기록째 내 컴퓨터로 처음 복사해 오는 것이에요. 한 번만 하면 돼요.

Claude Code 프롬프트 · 처음 한 번
요청: GitHub 저장소 [강사 아이디]/aipm-2026-assignments를 내 컴퓨터의 [Documents] 폴더에 클론해 줘.
내용: 클론이 끝나면 그 폴더로 이동해. submissions 아래에 [영문이름] 폴더가 있는지 확인하고, 없으면 만들지 말고 알려 줘. 다른 파일은 건드리지 마.
형식: 클론한 위치, 현재 브랜치 이름, 내 폴더 확인 결과.
  • 내 컴퓨터의 해당 폴더에 README.md와 submissions 폴더가 보이나요?

4-3. 매일 루틴: 받기 → 고치기 → 올리기

STEP 1. 작업 시작 전 최신 내용 받기 (pull)

Claude Code 프롬프트 · 시작할 때
요청: 작업을 시작하기 전에 GitHub에서 최신 내용을 받아 와 줘.
내용: 내가 아직 커밋하지 않은 변경이 있으면 받기 전에 알려 주고 멈춰. 충돌이 나면 직접 고치지 말고 어느 파일 어느 줄인지 보여 줘.
형식: 새로 받아 온 커밋 목록과 현재 상태 한 줄 요약.

STEP 2. 내 폴더에서 고치기

Claude Code 프롬프트 · 고칠 때
요청: submissions/[영문이름]/[날짜]/ 폴더에 오늘 과제 [파일 설명]을 만들어 줘.
내용: 내 폴더 밖의 파일은 만들거나 고치거나 지우지 마. 내가 말하지 않은 내용은 추가하지 마.
형식: 만든 파일 경로와 바뀐 내용 요약.

STEP 3. 커밋하고 올리기 (push)

Claude Code 프롬프트 · 올릴 때
요청: 바뀐 파일을 커밋하고 GitHub에 올려 줘.
내용: 커밋 전에 바뀐 파일 목록을 보여 주고, 내 폴더 밖의 파일이 섞여 있으면 멈추고 물어봐. 커밋 메시지는 [영문이름] [날짜] 과제 제출 형식으로 써. 강제 push는 하지 마.
형식: 실행한 Git 명령어와 결과, 올라간 커밋 메시지.
(선택) PR로 올리는 날의 프롬프트눌러서 펼쳐 보세요
Claude Code 프롬프트 · 브랜치와 PR
요청: 지금 변경을 새 브랜치 submit/[영문이름]-[날짜]에 커밋하고, main으로 향하는 PR을 만들어 줘.
내용: PR 제목은 [영문이름] [날짜] 과제로 써. 같은 파일을 고치는 내 PR이 이미 열려 있으면 새 PR을 만들지 말고 알려 줘. 강제 push는 하지 마.
형식: 브랜치 이름, PR 주소, PR에 포함된 파일 목록.
  • GitHub 저장소 화면에서 내 커밋(또는 PR)이 보이나요?
  • 커밋에 내 폴더 밖 파일이 섞이지 않았나요?

4-4. push가 거절될 때

여러 학생이 같은 저장소에 push하면 "먼저 받아오세요(fetch first)"라는 거절이 자주 나요. 충돌이 아니라 다른 학생이 먼저 올린 기록을 내 컴퓨터가 아직 모른다는 뜻이에요. 받아 와서 합친 뒤 다시 올리면 돼요. 서로 다른 파일만 고쳤다면 자동으로 합쳐져요.

Claude Code 프롬프트 · 거절됐을 때
요청: push가 거절됐어. 원인을 설명하고, 최신 내용을 받아 와서 다시 올려 줘.
내용: 받아 오는 중에 충돌이 나면 직접 고치지 말고, 충돌 파일과 양쪽 내용을 보여 주고 어느 쪽을 남길지 나에게 물어봐. 강제 push는 하지 마.
형식: 거절 원인 한 줄, 실행한 명령어, 최종 결과.
"강제로 올리면 된다"는 답이 나오면 멈춰요
강제 push는 다른 학생의 기록을 지울 수 있어요. 거절 메시지가 나오면 받아 오기(pull)가 먼저예요.
PART 5

팀 실습: 충돌을 일부러 만들고 강사가 해결하기

강사 계정의 과제 저장소 안에 팀별 폴더를 만들고, 팀마다 정상 흐름 → 케이스 A·B·C 순서로 상황을 만들어요. 충돌 PR은 학생이 억지로 풀지 않고 강사가 화면을 공유하며 해결해요.

5-1. 팀 폴더 만들기와 정상 흐름 확인

STEP 1. 강사: 팀 폴더와 공용 파일 만들기

[Add file] → [Create new file]에서 teams/team-1/README.md를 만들고 아래 내용을 넣어 main에 커밋해요. 팀 수만큼 반복해요.
teams/team-1/README.md · 팀 공용 파일
# 1팀

## 팀 목표
(여기에 한 줄)

## 팀원 한 줄 소개
- (여기에 추가)

STEP 2. 학생: 각자 자기 파일로 PR 올리기 (충돌 없음 확인)

팀원 모두 teams/team-1/영문이름.md를 새로 만들고, 3-3처럼 새 브랜치 + PR로 올려요.
강사가 PR을 아무 순서로나 하나씩 병합해요.
먼저 다른 PR이 병합된 뒤에도 나머지 PR에 충돌 표시 없이 [Merge pull request]가 눌리는지 다 같이 확인해요.
  • 파일이 서로 다르면 순서와 상관없이 병합된다는 것을 팀원 모두 확인했나요?

5-2. 케이스 A: 같은 학생이 같은 파일로 PR 두 개

상황 만들기 한 학생이 첫 번째 PR이 병합되기 전에 같은 파일, 같은 줄을 고치는 두 번째 PR을 또 열어요. 실제 수업에서는 "월요일 PR이 병합되기 전에 화요일 과제를 같은 파일로 또 제출"하는 모습으로 나와요.

STEP 1. 학생 1명: PR 두 개 만들기

main 기준으로 teams/team-1/kim-minji.md의 첫 줄을 오늘 배운 것: 커밋으로 고쳐 브랜치 try-a1로 PR을 열어요.
다시 main 화면에서 같은 파일 첫 줄을 오늘 배운 것: 브랜치로 고쳐 브랜치 try-a2로 두 번째 PR을 열어요.
강사가 try-a1 PR을 먼저 병합해요.

STEP 2. 강사: 충돌 확인과 해결

try-a2 PR 아래쪽에 충돌 때문에 병합할 수 없다는 안내와 [Resolve conflicts]가 보이는지 함께 확인해요.
같은 줄을 서로 다르게 고친 간단한 충돌이라 웹에서 풀 수 있어요. [Resolve conflicts]를 눌러 남길 문구만 두고 표시 줄 세 개를 지워요.
[Mark as resolved] → [Commit merge] → [Merge pull request] 순서로 눌러요.
충돌 화면에서 보이는 표시 예시
<<<<<<< try-a2
오늘 배운 것: 브랜치
=======
오늘 배운 것: 커밋
>>>>>>> main
더 간단한 해결: 오래된 PR 닫기
두 번째 PR이 첫 번째 내용을 모두 포함한다면 충돌을 풀지 않고 [Close pull request]로 닫은 뒤, 학생에게 최신 main에서 다시 올리게 해도 돼요.

예방 규칙 한 사람당 같은 파일의 PR은 하나만 열어 둬요. 고칠 게 더 있으면 같은 브랜치에 커밋을 더해요(3-3).

5-3. 케이스 B: 두 학생이 같은 파일명

상황 만들기 두 학생이 같은 위치에 같은 이름의 새 파일을 각각 PR로 올려요. 실제 수업에서는 둘 다 index.html을 같은 폴더에 올리는 모습으로 나와요.

STEP 1. 학생 2명: 같은 이름 파일로 PR 만들기

두 학생이 각자 teams/team-1/index.html을 서로 다른 내용으로 새로 만들어 각자 브랜치(try-b-kim, try-b-lee)로 PR을 열어요.
강사가 먼저 온 PR을 병합해요.

STEP 2. 강사: 충돌 확인과 해결

두 번째 PR에 충돌 안내가 뜨는지 확인해요. 이 충돌은 줄 단위 충돌이 아니어서 [Resolve conflicts]가 비활성화될 수 있어요.
해결 1 (웹, 권장): 두 번째 PR의 브랜치에서 그 파일을 열어 연필 버튼으로 편집하고, 파일 이름 칸을 lee-jun.html처럼 학생 이름으로 바꿔 같은 브랜치에 커밋해요. 같은 이름 파일이 없어지므로 충돌도 사라져요.
해결 2 (Claude Code): 웹 버튼이 비활성화돼 있고 파일 이름을 바꿀 수 없는 상황이면, 강사 컴퓨터의 Claude Code로 아래 프롬프트를 써요.
Claude Code 프롬프트 · 강사용 충돌 해결
요청: PR [번호]의 충돌을 해결해 줘.
내용: 그 PR의 브랜치를 받아 와서 main을 합쳐 봐. 충돌 파일과 양쪽 내용을 먼저 보여 주고, 어느 쪽을 남길지 나에게 물어본 뒤 해결해. 같은 이름의 새 파일 충돌이면 이 PR 쪽 파일 이름을 [학생 영문이름].html로 바꾸는 방법을 제안해. 강제 push는 하지 마.
형식: 충돌 파일 목록, 내가 고른 해결 방법, 올린 커밋과 PR 상태.

예방 규칙 파일 이름에 학생 이름을 넣어요. 공용 이름(index.html)은 학생 폴더 안에서만 써요.

5-4. 케이스 C: 공용 파일 하나를 여럿이 고침

상황 만들기 팀원 여럿이 팀 공용 README.md의 같은 자리에 동시에 한 줄씩 추가해요. 평소 개인 제출에는 해당하지 않고, PR로 문서를 함께 고칠 때 생기는 상황이에요.

STEP 1. 팀원 전체: 같은 자리에 한 줄씩 추가하기

팀원 모두 main 기준으로 teams/team-1/README.md를 열어 - (여기에 추가) 줄을 - 김민지: 기획자, 좋아하는 도구는 피그마처럼 자기 소개로 바꿔 각자 브랜치로 PR을 열어요.
강사가 한 PR을 병합하면 나머지 PR에 모두 충돌 안내가 떠요.

STEP 2. 강사: 하나씩 풀기 시연

두 번째 PR에서 [Resolve conflicts]를 눌러요. 이번에는 둘 중 하나를 고르지 않고 두 줄을 모두 남기고 표시 줄만 지워요.
[Mark as resolved] → [Commit merge] → [Merge pull request]를 눌러요.
다음 PR도 같은 방법으로 풀어요. 병합할 때마다 남은 PR이 다시 충돌할 수 있다는 것을 학생과 함께 확인해요.
두 줄 모두 남긴 결과 예시
## 팀원 한 줄 소개
- 김민지: 기획자, 좋아하는 도구는 피그마
- 이준: 마케터, 좋아하는 도구는 노션

예방 규칙 공용 파일은 한 번에 한 사람씩 고치거나, 팀원별 파일로 나눠요. 어느 내용을 남길지는 내용을 아는 사람(팀장, 강사)이 정해요.

5-5. 강사 해결 순서 한 장 정리

PR 화면에서 보이는 것강사가 할 일
충돌 없음, [Merge pull request] 활성리뷰 후 병합
[Resolve conflicts] 활성웹에서 풀기: 남길 내용 정리 → 표시 줄 삭제 → [Mark as resolved] → [Commit merge] → 병합
[Resolve conflicts] 비활성파일 이름 바꾸기로 충돌 원인을 없애거나, 강사 Claude Code로 로컬에서 해결 (5-3 프롬프트)
같은 내용의 PR이 중복오래된 PR을 [Close pull request]로 닫기
잘못 병합했다병합된 PR 화면의 [Revert]로 되돌리는 PR을 만들어 병합
남길 내용은 학생이 아니라 요구사항을 아는 사람이 정해요
AI 코딩 도구에게 충돌을 맡길 때도 "어느 쪽을 남길지 나에게 물어본 뒤 해결해"를 꼭 넣어요.

PART 6

응용: 제출 페이지에서 받아 PR로 쌓기

학생이 GitHub Pages로 만든 제출 페이지에서 파일을 올리면, 저장소에 브랜치와 PR이 자동으로 생기는 구조예요. 학생은 PR을 함께 검토하고, 강사가 병합해요. 설계안이므로 수업에 쓰기 전에 강사 계정으로 먼저 테스트해요.

6-1. 왜 Pages만으로는 안 되나

GitHub Pages는 HTML·CSS·자바스크립트 파일을 그대로 보여 주는 정적 호스팅이라 서버 코드를 실행하지 못해요. 저장소에 파일을 쓰려면 GitHub 열쇠(Personal Access Token)가 필요한데, 이 열쇠를 페이지 코드에 넣으면 브라우저 개발자 도구로 누구나 꺼내 갈 수 있어요. 그래서 열쇠를 숨겨 두는 중계 서버가 있어야 해요.

6-2. 구조와 구축 순서

전체 구조
[학생 브라우저]
   │ ① 제출 페이지 열기 (GitHub Pages, 공개 저장소)
   │ ② 닉네임 + 수업코드 + 파일 → 제출
   ▼
[구글 Apps Script 웹앱]   ← 열쇠(토큰)는 여기에만 보관
   │ ③ 수업코드 확인, 파일 이름 정리
   │ ④ 브랜치 만들기 → 파일 저장 → PR 열기
   ▼
[GitHub 과제 저장소 (비공개)]
   PR 목록에서 학생들이 검토·코멘트, 강사가 병합

STEP 1. 저장소 두 개 나누기 제출 페이지 저장소(공개, Pages용)와 과제 저장소(비공개)를 나눠요. 학생 결과물이 외부에 공개되지 않고, 누군가 올린 HTML이 우리 도메인에서 실행되지도 않아요.

STEP 2. 토큰 만들기 GitHub [Settings] → [Developer settings]에서 Fine-grained personal access token을 만들어요. 대상은 과제 저장소 하나만, 권한은 Contents 쓰기와 Pull requests 쓰기만, 만료일은 과정 종료일로 정해요. 브랜치 만들기는 Contents 쓰기 권한으로 처리돼요.

STEP 3. Apps Script 중계 서버 만들기 토큰은 코드에 쓰지 않고 스크립트 속성(Script Properties)에 저장해요. doPost에서 수업코드 확인 → 파일 이름 정리(영문·숫자·하이픈, 앞에 제출 시각) → 브랜치 생성(Git references API) → 파일 저장(Contents API) → PR 생성(Pull requests API) 순서로 처리하고, 웹앱으로 배포해요.

STEP 4. 제출 페이지 배포와 테스트 공개 저장소에 제출 페이지를 만들어 Pages로 배포하고, 강사 계정으로 테스트 제출을 해서 과제 저장소에 브랜치와 PR이 생기는지 확인해요.

6-3. 한계와 운영 수칙

항목내용
작성자 표시브랜치와 PR은 토큰 주인(강사) 계정으로 만들어져요. 누가 제출했는지는 PR 제목과 본문의 닉네임으로 구분해요.
본인 확인닉네임은 누구나 사칭할 수 있어요. 출석·평가에 쓰려면 학생별 고유 코드를 따로 나눠 줘요.
검토 단계제출은 익명이어도, PR을 보고 코멘트하려면 학생도 GitHub 계정으로 초대돼 있어야 해요.
충돌학생별 파일이면 충돌하지 않아요. PART 5의 케이스 A·B·C와 같은 조건에서만 생겨요.
Git 실습 범위PR 검토·코멘트·병합은 경험하지만, 브랜치를 만들고 PR을 여는 행동은 서버가 대신해요. 직접 해 보는 연습은 PART 3·4에서 해요.
스팸·용량수업코드를 주 단위로 바꾸고, 허용 확장자(html, md, png, jpg, pdf)만 받아요. Apps Script의 처리 용량 한도는 실제 파일로 테스트해요.
