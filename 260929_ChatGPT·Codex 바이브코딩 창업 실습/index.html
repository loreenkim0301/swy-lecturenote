INTRO

1.1 창업자에게 바이브코딩이 필요한 이유

창업자가 모든 코드를 직접 작성할 필요는 없습니다. 다만 아이디어를 AI에게 설명하고 빠르게 화면으로 확인할 수 있다면 개발 전에 사업 아이디어를 구체화하고 다른 사람에게 보여주며 빠르게 검증할 수 있습니다.

01

02

문구·색상·구성을 AI와 대화하며 변경합니다.

03

직접 공유

완성된 결과를 URL로 만들어 고객·동료에게 보여줍니다.

빠른 생성은 완성의 의미가 아니라 검증의 시작입니다.
AI가 만든 내용과 기능이 실제 사업에 적합한지는 사람이 직접 확인해야 합니다.
현장에서 바이브코딩을 쓰는 이유
1. 대표가 상상한 화면을 기획자·개발자에게 더 빠르게 전달할 수 있습니다.
2. 회사 홈페이지나 앱의 프로토타입까지는 어느 정도 직접 구현해볼 수 있습니다.
3. 기획·디자인·개발의 흐름을 직접 경험하면서 각 직무에 대한 이해도를 높일 수 있습니다.

1.3 프로덕트·프로토타입·MVP: 작게 만들고, 빨리 배우기

아래는 일반적으로 창업자나 기획자가 서비스를 처음 만들어야 할 때 알아야 할 필수 기초 용어들입니다.

1. 용어 정의

PRODUCT

프로덕트

고객의 문제를 해결하는 제품·서비스와 경험 전체입니다. 화면에서 시작해 주문, 배송, 배송 완료까지 고객이 실제로 겪는 사용자 흐름도 포함합니다.

PROTOTYPE

프로토타입

아이디어와 사용자 흐름을 빠르게 확인하는 초기 모형입니다. 실제 결제나 배송이 작동하지 않아도 되며, 고객이 서비스를 이해하고 사용할 수 있는지 확인하는 데 씁니다.

MVP

최소 기능 제품

고객이 핵심 가치를 실제로 얻는지 확인하는 가장 작은 서비스입니다. 기능을 적게 넣는 것이 목적이 아니라, 가장 중요한 가정을 실제로 검증하는 것이 목적입니다.

세 용어의 관계
프로덕트는 고객에게 계속 가치를 주는 전체 서비스입니다. 프로토타입은 그 서비스의 아이디어와 흐름을 보여주는 모형이고, MVP는 고객이 실제로 써 보며 가치를 확인할 수 있는 가장 작은 운영 형태입니다.

2. 동네 반찬 정기배송 서비스 바이브코딩 사례

가상의 창업자가 “퇴근 후 저녁 준비가 부담스러운 직장인에게 주 1회 반찬을 배송한다”는 아이디어를 갖고 있다고 가정해보겠습니다. 이 서비스의 프로덕트는 홈페이지 하나가 아니라 메뉴 선택, 신청, 배송, 재주문까지의 경험 전체입니다.

바이브코딩을 모를 때

머릿속 아이디어를 글로만 정리한 뒤, 개발자나 제작 업체에 “반찬 주문 앱을 만들고 싶다”고 의뢰하기 쉽습니다. 어떤 화면이 필요한지, 고객이 어떤 순서로 신청하는지 직접 확인하기 어렵고, 수정 요청이 늘어날수록 시간과 비용도 커집니다.

처음부터 앱·결제·배송관리 기능을 모두 만들려 하면, 고객이 실제로 주문할지 확인하기 전에 큰 비용이 들어갈 수 있습니다.

↔
바이브코딩을 알 때

비개발자도 AI에게 서비스 설명을 입력해 메뉴, 가격, 신청 버튼이 있는 한 장의 화면을 먼저 만들 수 있습니다. 이 화면을 고객에게 보여주며 메뉴와 가격, 신청 흐름을 이해하는지 확인한 뒤 필요한 기능만 다음 단계에서 개발합니다.

바이브코딩은 개발자를 완전히 대신하는 일이 아니라, 창업자가 더 구체적인 화면과 요구사항으로 검증·협업하는 방법입니다.

3. 참고: 비개발자 창업자도 할 수 있는 내 아이디어 검증 과정

처음부터 주문 앱을 만들 필요는 없습니다. 아래 수준이면 초기 검증을 시작할 수 있습니다.

1. 한 사람 정하기“퇴근이 늦은 1인 가구 직장인”처럼 처음 고객을 한 유형으로 좁힙니다.
2. 한 가지 행동 정하기고객이 주간 메뉴를 보고 ‘신청하기’를 누르는 흐름 하나만 정합니다.
3. AI로 화면 만들기ChatGPT나 Codex에 메뉴, 가격, 배송 요일, 신청 버튼이 있는 한 장의 웹페이지를 요청합니다.
4. 실제 고객에게 보여주기대상 고객 3명에게 화면을 보여주고, 어떤 메뉴를 고르는지와 신청이 망설여지는 이유를 기록합니다.
프로토타입에서 확인할 것
고객이 서비스가 무엇인지 10초 안에 이해하는가? 메뉴와 가격을 보고 신청 의향이 생기는가? 신청 버튼을 자연스럽게 찾는가?
MVP로 넘어가는 가장 현실적인 방법
화면에서 반응이 좋다면, 결제 시스템부터 만들기보다 카카오톡 채널·전화·간단한 신청 폼으로 10~20가구의 신청을 먼저 받아봅니다. 정해진 요일에 직접 배송하거나 기존 배송 수단을 활용해, 재주문 의향과 운영 부담을 확인합니다.
아직 만들지 않아도 되는 것
자동 결제, 배달 기사 배정, 개인화 추천, 리뷰 시스템, 고객용 앱입니다. 반복 주문과 운영 방식이 확인된 뒤에야 시간과 비용을 들여 개발할 이유가 생깁니다.
바이브코딩의 현실적인 범위
비개발자는 AI를 활용해 화면, 문구, 기본 흐름, 간단한 신청 페이지를 빠르게 만들고 수정할 수 있습니다. 다만 결제·개인정보·주문 데이터·배송 연동처럼 실제 운영에 영향을 주는 기능은 보안과 법적 책임이 따르므로 검증된 서비스나 개발자의 도움을 받아야 합니다.

실습 A. 파일을 첨부해 데이터 동적 대시보드 만들기

핵심 경험: 엑셀·CSV 파일을 첨부하면 AI가 실제 데이터를 읽고 표와 그래프로 시각화할 수 있다는 점을 확인합니다.

1. 실습용 매출 데이터 파일을 다운로드합니다.
매출 약 5억 원 규모의 1인 쇼핑몰을 가정한 예제 데이터입니다. Excel에서 열 수 있는 CSV 파일입니다.
2. Chat에서 새 대화를 엽니다.
다운로드한 파일을 입력창의 파일 첨부 버튼으로 첨부합니다.
3. 초기 대시보드를 만듭니다.
파일 첨부가 끝난 뒤 아래 1차 프롬프트를 입력합니다.
실습 A · 3. 초기 대시보드 만들기
첨부한 파일의 매출 데이터를 분석해서 한 페이지짜리 대시보드를 만들어줘.

- 상단에는 총매출·총이익·마진율 요약 카드
- 가운데에는 월별 매출 추이 그래프
- 하단에는 상품별 매출 표
- 첨부한 파일의 실제 데이터만 사용

2.3 본격 실습 — 홈페이지 프로토타입 만들기

대시보드·계산기·체크리스트 실습은 여기서 종료합니다. 이제 새 대화를 열고, 하나의 홈페이지를 처음부터 만들고 수정하는 실습을 시작합니다. 이 파트부터는 하나의 홈페이지 프로토타입을 계속 생성·수정합니다. 예시 프롬프트 안에서는 가상의 서비스명 ‘LocalLink’를 사용합니다.

전문 용어보다 원하는 결과를 설명하는 데 집중합니다.
HTML·CSS·JavaScript 같은 용어를 직접 알거나 작성할 필요는 없습니다. 누구를 위한 홈페이지인지, 어떤 내용이 필요한지, 어떤 버튼이 동작해야 하는지를 설명하면 AI가 화면과 코드를 만들어줍니다.
Chat에서 ‘새 대화’를 시작합니다.
다른 실습과 구분하기 위해 홈페이지 제작용 대화를 새로 엽니다.
아래 프롬프트를 입력해 프로토타입을 생성합니다.
대상·구성·동작·디자인을 나누어 설명하면 원하는 결과를 더 정확하게 전달할 수 있습니다.
생성된 화면을 미리보기로 확인합니다.
핵심 소개, 제공 가치 3개, 이용 과정 3단계, 문의 영역이 모두 있는지 확인합니다.
홈페이지 프로토타입 생성 프롬프트
가상의 스타트업 'LocalLink'의 회사 소개 홈페이지를 만들어줘.

[대상]
지역 소상공인과 협업하려는 브랜드 담당자

[구성]
- 상단 회사 소개
- LocalLink가 제공하는 가치 3개
- 이용 과정 3단계
- 문의 영역

[동작]
'협업 방식 보기' 버튼을 누르면 이용 과정 영역으로 이동

[디자인]
- 신뢰감 있는 남색과 밝은 배경
- 글자를 충분히 크게 구성
- 스마트폰에서도 보기 편한 화면

결과를 바로 확인할 수 있도록 미리보기 가능한 형태로 만들어줘.
프롬프트를 이렇게 나누는 이유
전문 개발 용어를 사용하기 위한 것이 아니라, 대상 → 구성 → 동작 → 디자인처럼 원하는 결과를 빠뜨리지 않고 설명하기 위해서입니다. 수강생은 코드를 직접 작성하지 않습니다.
CHECK & REFINE

2.4 프로토타입 결과 확인 → HTML 저장·로컬 실행 → 수정

2.3에서 만든 프로토타입을 그대로 이어서 진행합니다. 생성 → 확인 → 저장 → 로컬 실행 → 수정 → 재확인 순서로 한 번 끝까지 경험합니다.

생성된 프로토타입을 미리보기로 확인합니다.
요청한 섹션이 모두 있는지, 버튼이 의도대로 동작하는지, 모바일 화면에서 글자와 버튼이 겹치지 않는지 확인합니다.
AI가 코드 블록으로 답했다면 전체 코드를 index.html로 저장합니다.
파일 이름의 확장자가 .html인지 확인합니다.
저장한 index.html을 더블클릭해 브라우저에서 엽니다.
인터넷에 공개된 것이 아니라 내 컴퓨터에서만 확인하는 로컬 실행입니다.
화면을 보고 수정할 부분을 정합니다.
처음부터 코드를 직접 고치지 않고, 같은 Chat 대화에서 자연어로 수정 요청합니다.
수정 프롬프트 — 초보자용 표현
현재 홈페이지에서 다음 부분만 수정해줘.

- 메인 제목을 더 짧게 정리
- '협업 방식 보기' 버튼을 더 눈에 띄게 수정
- 모바일에서는 좌우 여백을 20px 이상 유지

다른 문구와 섹션 순서, 버튼 동작은 변경하지 말아줘.
수정된 결과를 다시 확인합니다.
요청한 부분만 바뀌었는지 확인합니다.
HTML 파일을 다시 저장하고 브라우저를 새로고침합니다.
로컬 파일에도 최신 수정 내용이 반영됐는지 확인합니다.
여기까지는 아직 ‘배포’가 아닙니다.
브라우저에서 화면이 잘 열리더라도 파일이 내 컴퓨터에만 있다면 다른 사람은 접속할 수 없습니다. 다음 파트에서는 이 결과를 사이트 형태로 공유하거나, 이후 Codex·GitHub·Vercel을 이용해 실제 웹주소로 배포하는 흐름으로 이어집니다.

GitHub 계정을 준비합니다.
계정이 없다면 무료 계정을 만들고 이메일 인증을 완료합니다.
↗ GitHub 무료 계정 만들기

ChatGPT 데스크톱 앱의 왼쪽 상단에서 Codex로 전환합니다.
일반 Chat 화면과 다른 Codex 작업 화면이 열리는지 확인합니다.

수업용으로 새 폴더를 만들고 해당 폴더를 Codex에서 엽니다.
아래 프롬프트를 입력해 웹 프로젝트를 생성합니다.
Codex 프로젝트 생성 프롬프트
가상의 스타트업 'LocalLink'의 회사 소개 홈페이지를 단일 HTML 파일로 만들어줘.

[완료 기준]

GitHub에 소스코드 업로드하기

Codex에서 웹페이지 제작을 완료했다면, 배포를 위해 생성된 파일을 GitHub Repository에 업로드합니다.

💡 GitHub 플러그인을 연결했는데도 바로 업로드되지 않나요?
ChatGPT의 GitHub 앱 연결은 기본적으로 승인한 Repository의 내용을 읽고 분석하기 위한 연결입니다. 이 연결만으로 로컬 프로젝트의 Git push 인증이 자동으로 완료되는 것은 아닙니다.
코드를 생성·편집하고 GitHub에 직접 push하는 작업은 Codex에서 할 수 있지만, 로컬 환경의 GitHub 인증이나 원격 Repository 연결이 추가로 필요할 수 있습니다.
이 실습에서는 초보자도 쉽게 진행할 수 있도록 GitHub 웹사이트에서 파일을 직접 업로드합니다.
자연어로 push를 요청하는 방법도 사용할 수 있지만, 계정 인증이나 원격 저장소 연결 상태에 따라 실패할 수 있으므로 수동 업로드를 기본 방법으로 진행합니다.

방법 A. GitHub 웹사이트에서 직접 업로드

GitHub에서 새 Repository를 만듭니다.
GitHub에 로그인한 뒤 New repository를 선택하고 저장소 이름을 입력해 생성합니다.
↗ GitHub 새 Repository 만들기
파일 업로드 화면을 엽니다.
빈 Repository의 Quick setup → uploading an existing file을 선택합니다. 이미 파일이 있는 Repository라면 Add file → Upload files를 선택합니다.
Codex가 만든 프로젝트 파일을 업로드합니다.
생성된 index.html과 필요한 파일을 화면에 드래그하거나 choose your files로 선택합니다.
Commit changes를 누릅니다.
업로드할 파일을 확인한 뒤 Commit changes를 눌러 Repository에 저장합니다.
Code 화면에서 실제 파일을 확인합니다.
index.html 등 홈페이지 파일이 Repository 목록에 보이면 업로드 완료입니다.
업로드 순서
새 Repository 생성 → uploading an existing file → HTML 파일 추가 → Commit changes → 파일 목록 확인

방법 B. Codex에 자연어로 push 요청

GitHub 인증과 원격 저장소 연결이 정상적으로 되어 있다면 Codex에 자연어로 업로드를 요청할 수도 있습니다.

GitHub에 소스코드 올리기
현재 프로젝트의 소스코드를 방금 만든 GitHub Repository에 올려줘.

- 현재 프로젝트 파일 전체를 확인
- Git 저장소 초기화가 필요하면 진행
- 변경 내용을 커밋
- 연결한 GitHub Repository의 main 브랜치로 push

각 단계에서 권한 승인이나 내가 확인해야 할 작업이 있으면 먼저 알려줘.
원격 GitHub 저장소가 연결되지 않은 경우
Codex가 다음과 같이 안내할 수 있습니다.

“푸시할 GitHub 저장소 주소가 아직 연결되어 있지 않습니다. 방금 만든 저장소의 HTTPS 또는 SSH URL을 보내주시면 원격을 연결하고 main으로 push하겠습니다.”

이 경우 GitHub Repository의 Code 버튼에서 HTTPS 또는 SSH 주소를 복사해 Codex에 전달한 뒤 다시 push를 요청합니다.
어떤 방법을 사용하든 GitHub 웹사이트에서 마지막 확인을 합니다.
Repository에 index.html 등 실제 소스코드가 보이는지 확인합니다.
GitHub에 파일이 올라간 것을 확인한 뒤 4.4로 이동합니다.
Vercel은 이 Repository의 소스코드를 가져와 배포하므로, 파일이 보이지 않으면 아직 다음 단계로 넘어가지 않습니다.
