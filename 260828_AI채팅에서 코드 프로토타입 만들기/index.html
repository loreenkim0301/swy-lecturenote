캔버스 vs 아티팩트 —
일반 채팅으로 HTML 프로토타입 만들기

챗지피티 · 클로드 · 제미나이, 별도 코딩 툴 없이 일반 채팅창 프롬프트만으로 도구 안에 내장된 아티팩트·캔버스·코드블록 미리보기로 프로토타입을 바로 확인하고 수정하는 방법을 비교합니다. .html 파일로 내보내는 것은 배포·공유가 필요할 때만 거치는 선택 단계입니다.

01 · Baseline

세 도구의 공통 전제

챗지피티·클로드·제미나이는 화면 구성은 다르지만, 실습에서 다루는 방식의 기본 전제는 같습니다.

1

핵심은 “미리보기”로 바로 확인하는 것

세 도구 모두 프롬프트만으로 아티팩트·캔버스·코드블록 안에서 화면을 즉시 확인하고, 이어지는 프롬프트로 계속 고쳐나갈 수 있습니다. 실습의 대부분은 이 미리보기 화면 안에서 끝납니다. .html 파일로 내보내는 것은 배포·공유가 필요할 때만 거치는 선택 단계입니다.

2

대화 길이(토큰) 한도에 미리 대비

한 서비스에서 대화가 길어져 한도가 소진되면, 지금까지의 코드 전체를 복사해 다른 서비스나 새 계정으로 옮겨 미리보기 작업을 이어갑니다.

3

공유 정책은 요금제에 따라 갈림

수업 당시 확인된 내용으로는, 무료 요금제 결과물은 외부 공유 링크 생성이 자유롭고 유료 요금제는 외부 공유가 더 까다로웠습니다. 각 서비스의 공유 정책은 자주 바뀌므로 실제 수업 전 최신 화면으로 재확인을 권장합니다.

4

(선택) 파일로 내보낼 땐 파일명이 반드시 index

배포가 필요해 .html로 내보낼 때는 macOS는 index.html을 그대로, Windows는 확장자 없이 index만 남겨야 합니다. 이름에 .html이 중복되면 배포 시 오류가 납니다.

04 · Walkthrough

실습 흐름 예시 — 챗지피티 기준

채용 플랫폼 데스크탑 화면을 캡처해 프로토타입으로 옮긴 실습 사례를 그대로 재구성했습니다. 같은 흐름을 클로드·제미나이에도 적용할 수 있습니다.

01

화면 캡처를 올리고 역할·목표를 지정

이미지를 첨부하고, AI에게 역할과 최종 목표를 먼저 명확히 알려줍니다.

나는 기획자이고, 너는 UXUI디자이너&퍼블리셔이다. 위의 이미지는 데스크탑 버전의 웹사이트 이미지이다. 나의 목표는 이미지를 분석해서 웹사이트 코드로 만들고, 프로토타입으로 바꾸고 싶다.
02

IA(정보구조)를 표로 정리해 개선점부터 확인

코드보다 먼저 AS-IS/TO-BE 구조표로 화면 단위를 맞춥니다. 이 단계를 건너뛰면 이후 수정 요청이 산발적으로 흩어지기 쉽습니다.

03

캔버스로 코드를 합쳐 미리보기 — 핵심 단계, 여기서 확인·반복 수정

전체 프로토타입 코드를 1개의 파일로 합치고, '캔버스 기능'을 통해서 미리보기 하게 해줘.

캔버스 화면에서 결과를 확인하고, 마음에 안 드는 부분은 다시 프롬프트로 고칩니다. 실습·검토는 대부분 이 미리보기 화면 안에서 끝납니다.

04

(선택) 배포·공유가 필요하면 .html로 내보내기

미리보기만으로 충분하면 이 단계는 건너뛰어도 됩니다. 다른 사람에게 파일로 전달하거나 Netlify 등에 올려야 할 때만, 캔버스 우측 상단 두 번째 다운로드 버튼으로 index.html을 받습니다.

05

결과물 공유 — 링크 두 종류를 헷갈리지 않기

대화 프롬프트 공유 링크와 프로토타입(캔버스) 공유 링크는 서로 다른 URL입니다. 협업자에게는 보통 둘 다 필요합니다.

06

오류 대응 — 미리 다운로드, 맥락 유실 시 재투입

캔버스 결과물은 완성될 때마다 04단계 방식으로 미리 다운로드해 둡니다. AI가 이전 맥락을 잃으면, 갖고 있는 마지막 .html 파일을 다시 넣고 처음부터 요청하는 편이 빠릅니다.

05 · Trade-off

피그마 프로토타입, 대체할 수 있나

수업에서 다룬 평가 5가지입니다. 결론은 전부 “가능”이지만, 조건이 붙습니다.

Y

피그마의 애니메이션 프로토타입 — 클로드·제미나이·챗지피티로도 재현 가능

Y

무료 요금제 사용 시 프롬프트·프로토타입 외부 공유가 자유로움

Y

유료 요금제 사용 시에는 반대로 외부 공유가 더 어려움 (당시 확인 기준, 정책 변경 가능)

Y

원하는 실제 데이터를 넣어 화면을 커스텀할 수 있음

Y

이미지를 기반으로 화면을 하나씩 만들며 점진적으로 확장 가능

단, 결과물은 결국 1개의 .html(또는 .jsx) 파일입니다. 컴포넌트 분리, 상태관리, 실제 배포 아키텍처가 필요한 “진짜 개발”과는 차이가 있을 수 있다는 전제를 깔고 써야 합니다.
06 · Field notes

실전 사례 — 성공과 실패

같은 과정 수강생들의 실습에서 반복적으로 나온 패턴만 추려 익명화했습니다.

막힘

챗지피티가 응답을 멈춤 (새로고침·재시작으로도 복구 안 됨)

작업 중이던 코드가 있다면 그대로 두고, 마지막으로 받은 코드 전체를 제미나이 새 대화에 넣고 이어가는 방식으로 우회했습니다.

전환

캡처 이미지를 넣었는데 결과가 원본과 많이 다름

이미지 인식 결과물이 챗지피티에서 원본과 크게 다르게 나온 경우, 제미나이로 같은 이미지를 먼저 분석시켜 코드를 뽑고, 그 코드를 챗지피티에 옮겨 “같은 문법으로 이어서 만들어줘”라고 요청하니 후처리가 줄었습니다.

모호한 프롬프트

“가장 작은 화면일 때 A 영역을 제외하라” → 모든 화면이 모바일처럼 바뀜

지시 대상과 결과 상태를 함께 명시하지 않으면 AI가 범위를 넓게 해석합니다. “반응형 처리 시 A 영역은 사라지고 B 영역만 남도록 수정해줘”처럼 대상·조건·결과를 한 문장에 묶으니 의도대로 반영됐습니다.

비효율

캔버스 코드가 좌측 프롬프트로 잘 수정되지 않음

부분 수정 요청이 반영되지 않아 결국 전체 코드를 다시 받아 수동으로 교체했습니다. 코드가 길어질수록 세션 자체가 무거워지는 부작용이 있었습니다.

착시

스켈레톤 UI 요청 결과를 “로딩 중”으로 착각

완성도 높은 로딩 애니메이션이 포함된 결과물을, 아직 로딩 중인 화면으로 오인해 한참 기다린 사례입니다. 스켈레톤 UI를 요청할 때는 “완성 상태”와 “로딩 상태”를 구분해 캡처해 두는 편이 안전합니다.

07 · Checklist

하드 리프레시로 캐시부터 배제

Mac은 ⌘+Shift+R, Windows는 Ctrl+F5. 수정이 반영 안 된 것처럼 보일 때 가장 먼저 시도합니다.

3단계로 나눠 버그를 특정

① 채팅 화면 미리보기 새로고침 → ② 다운받은 .html이 브라우저에서 정상 동작 → ③ 배포 후 재확인. 어느 단계에서 깨졌는지 구간을 좁힙니다.

콘솔에서 실제 에러 확인

마우스 우클릭 → 검사 → 콘솔 탭. 화면에는 안 보여도 에러 메시지는 대부분 여기 있습니다.

Netlify Drop으로 즉시 배포
